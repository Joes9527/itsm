## 1. 现状核实（代码走查，2026-08-07）

### 1.1 SR 审批：硬编码三段式，且存在新旧两套并行实现

| 实现 | 路由 | 位置 | 状态 |
|---|---|---|---|
| 旧实现 | `/services/requests/...`（`router.go:1263-1269`） | `service/service_request_service.go`（`CreateServiceRequest`，L104-157）+ `controller/service_controller.go` | `totalLevels := 3` 与三段步骤硬编码；`ServiceCatalogItem.ApprovalChainID` 有取值但代码里只留一行 `// TODO: 根据审批链ID获取审批级别配置 // 暂时使用默认配置`，**完全未生效** |
| 新实现（当前实际生效路径） | `/service-requests`（`router.go:877`，租户组下） | `handlers/service_request/service.go`（`Service.Create`，L141-164） | 同样硬编码 `{1,Manager,24h},{2,IT,48h},{3,Security,72h}` |

两套实现审批人合法性校验都很粗糙：`checkEligibility()`（`handlers/service_request/service.go:327-348`）是字符串比对——`role=="manager" && actorDept==requesterDept` 才能批主管节点，`role in {agent,technician}` 批IT节点，`role=="security"` 批安全节点。**没有金额分级、没有组织层级判断、没有规则表**。

这违反了仓库 `CLAUDE.md` 里"不要在两处实现同一域端点"的要求，本设计的前置技术债是**先收敛为一套实现**（见第 7 节）。

### 1.2 "审批矩阵"雏形已建表，但未接入 SR 主流程

`ent/schema/approvalchain.go` 已经有相当接近"审批矩阵"的结构，且 `entity_type` 字段的注释里已经预留了 `service_request`：

```go
field.String("entity_type").Default("ticket"), // ticket, change, service_request
field.JSON("chain", []ApprovalChainStep{})

type ApprovalChainStep struct {
    Level        int
    ApproverID   int
    Role         string // manager, it_admin, security_admin
    IsRequired   bool
    ApprovalType string // serial | parallel
    Threshold    int    // 会签投票阈值
}
```

但目前只有 ticket 域在用，`handlers/service_request/service.go` 和 `service/service_request_service.go` 都没有查询过这张表。另外 `ent/schema/servicecatalog.go` 里的 `requires_approval`（生效）、`approval_level`、`approvers []int`（均未被两套 Create 逻辑引用）——是死字段。

### 1.3 超时升级：字段已加，没有引擎消费

`ent/schema/servicerequestapproval.go` 已经是"V1 增强"版本，字段和索引都已就位：

```go
field.Int("timeout_hours").Default(24)
field.Time("due_at").Optional()
field.Bool("is_escalated").Default(false)
field.Int("delegated_to_id").Optional().Nillable()
field.String("escalation_reason").Optional()
// 索引: index.Fields("due_at"), index.Fields("status", "due_at")
```

`due_at` 在创建审批记录时会被计算写入，但全仓库没有任何定时任务扫描它——`is_escalated`/`delegated_to_id`/`escalation_reason` 目前是**写得进去、读不出来**的字段。

### 1.4 组织模型：只有"单层租户 + 租户内部门树"，没有集团-分公司层级

- `ent/schema/tenant.go`：`parent_tenant_id`（可空 int，注释"MSP客户指向MSP提供商"）+ `msp_provider_id`。这是**两层弱指针**，`service/tenant_service.go` 只有基础 CRUD，**没有递归查询上下级租户的方法**，也没有深度限制。
- `ent/schema/msp_allocation.go`：`msp_user_id` + `customer_tenant_id` + `role(primary|backup|specialist)`——这是"服务商代运维客户"的协作关系，语义上和"集团管控分公司审批权"不同，**不建议复用**，否则未来 MSP 客户与集团分公司两个概念会在同一批字段上打架。
- `ent/schema/department.go`：`parent_id` 自引用 + 真实的树查询实现（`departments/tree` 路由，`service/department_service.go`）。**这是仓库里唯一真正落地的多级树**，但 `tenant_id` 是 `Positive()` 必填，天然租户内隔离，无法表达"分公司作为独立法人/独立租户，同时又要汇总到集团"的诉求。

### 1.5 BPMN 引擎能力边界（`nitram509/lib-bpmn-engine v0.2.4`）

查过库源码（`~/go/pkg/mod/github.com/nitram509/lib-bpmn-engine@v0.2.4`）：

- 官方 README 明确标注 **"beta" status, not recommended to use in production**；
- 网关只有 `ParallelGateway` / `ExclusiveGateway` / `EventBasedGateway`，**没有 InclusiveGateway**；
- 定时器只支持 **Intermediate Timer Catch Event**，全仓库无 "Boundary" 命中，**不支持边界定时器**；
- 全仓库 grep `MultiInstance`/`dmn` **零命中**，**不支持原生多实例任务，不支持 DMN 决策表**；
- 现有"会签"（`service/bpmn_process_engine.go:2146` `CreateCounterSignTasks`）是应用层用 `parent_task_id`/`root_task_id` 手工建多个平级子任务模拟的，**不是**调用库的原生能力（因为库没有这个能力）——`docs/architecture/approval-node-semantics.md` 里"BPMN原生Multi-Instance"的表述需要在后续修订中更正；
- `service/bpmn/bpmn_group_resolver.go` 已实现"候选组名 → 按 tenant_id 展开具体用户"的逻辑（`WithMembers()`），是目前唯一的"半动态"审批人解析，但只服务于 BPMN userTask，未接入 SR。

**结论：SR 的集团化动态审批不应该假设可以直接套用 BPMN 引擎的原生能力去做，需要在应用层自建审批链解析器和超时扫描任务**（做法上可以参考现有 `CreateCounterSignTasks` 的"应用层实现，不依赖引擎原生能力"路子）。

| # | 目标能力 | 现状 |
|---|---|---|
| 1 | 按 SR 类型/金额/风险动态选择审批链 | 硬编码三段，`ApprovalChain` 表建了但未接入 |

## 3. 设计目标

1. 复用已有的 `ApprovalChain` / `ApprovalChainStep` 结构做审批矩阵，不新建平行的一套"审批配置表"（修正 `实施建议.md` 阶段二里"新建 `service_request_approval_config` 表"的提法）。
2. 新增一个独立于 `Tenant.parent_tenant_id` 的组织层级模型，专门表达"集团-分公司"法人层级，与 MSP 的服务商-客户语义解耦。
3. 新增审批链解析服务（应用层，不依赖 BPMN 引擎），输入 SR 请求，输出具体到人的有序审批链，写入 `ServiceRequestApproval.node`（该字段本来就是"审批步骤配置快照"，正好承载解析结果，不需要新表）。
4. 新增超时扫描后台任务，消费已经存在的 `due_at` / `is_escalated` 字段。
5. 明确收敛两套 SR 实现为一套，作为本设计能落地的前置条件。

## 4. 总体方案

### 4.1 组织模型：新增 OrgUnit，而不是扩展 Tenant.parent_tenant_id

两个选项对比：

| 方案 | 做法 | 问题 |
|---|---|---|
| A：扩展 `Tenant.parent_tenant_id` | 给 Tenant 补递归查询服务 | `parent_tenant_id` 现有语义是"MSP客户→MSP提供商"，`msp_allocation.role` 是运维协作角色（primary/backup/specialist），不是审批授权角色。复用会导致"MSP客户"和"集团分公司"两个业务概念在同一批字段上混淆，未来任何一方加字段都可能误伤另一方 |
| **B：新增独立的 `OrgUnit` 表（推荐）** | 表达"集团-分公司-（部门）"法人/管控层级，与 Tenant 关联而非复用 | 需要新表，但语义干净，且可以和现有 `Department` 树共存：分公司对应一个 `OrgUnit`，分公司内部仍用现有 `Department` 树，`Department` 增加可选 `org_unit_id` 字段挂接，不破坏现有 `tenant_id` 强隔离 |

推荐方案 B。`OrgUnit` 字段草案（风格对齐现有 `tenant.go`/`department.go`）：

```go
// OrgUnit：集团/分公司层级的组织节点，独立于 Tenant 的技术隔离边界
field.String("name")
field.String("code").Unique()
field.String("org_type")        // group | subsidiary
field.Int("parent_org_unit_id").Optional()   // 自引用，集团为空
field.Int("tenant_id").Optional()            // 若分公司对应独立租户则关联，否则为空（同租户下的虚拟层级）
field.String("legal_entity_code").Optional() // 呼应 Tenant 已有的同名字段，做对账关联
field.Int("level").Default(0)                // 冗余存储层级深度，避免每次递归计算
```

`Department` 增加：

```go
field.Int("org_unit_id").Optional() // 可选：明确该部门归属的分公司节点
```

需要新增的服务能力（设计层面，不含代码）：`OrgUnitService` 提供"取组织树""取某节点的完整上级链""取某节点向下的所有子节点"三个递归查询方法——这是当前 `tenant_service.go`/`department_service.go` 都不具备的能力，必须新建。

### 4.2 审批矩阵：扩展 `ApprovalChainStep`，接入 `entity_type=service_request`

`ApprovalChainStep` 当前维度只有 `Level/Role/ApprovalType/Threshold`，扩展为：

```go
type ApprovalChainStep struct {
    Level        int
    Role         string
    ApprovalType string // serial | parallel
    Threshold    int

    // 新增字段
    OrgScope         string  `json:"org_scope,omitempty"`          // subsidiary | group，标记这一步是分公司层还是集团层
    AmountThreshold  float64 `json:"amount_threshold,omitempty"`   // 超过该金额才追加此步骤
    GroupControlled  bool    `json:"group_controlled,omitempty"`   // 命中集团统一管控目录时，无论金额都追加
}
```

`ApprovalChain.entity_type = "service_request"` 直接复用现有表和索引（`index.Fields("tenant_id","entity_type")` 已经支持按租户+类型查询），不需要新表——这是对 `实施建议.md` 阶段二"新建 `service_request_approval_config` 表"的修正：该能力已经有表，缺的是接入代码和维度扩展。

### 4.3 审批链解析服务（应用层新组件）

输入：`SR类型、金额、风险等级、申请人 org_unit_id`
逻辑（与第 1.5 节结论一致，不依赖 BPMN 引擎原生能力）：

1. 查 `ServiceCatalog.approval_level` 命中的 `ApprovalChain`（`entity_type=service_request`）取规则模板；
2. 若模板步骤标记 `GroupControlled=true`，链条恒定追加集团层节点；
3. 若模板步骤有 `AmountThreshold`，沿 `OrgUnit` 树从申请人节点向上核对，直到某一层级额度覆盖金额或到达集团顶点；
4. 两类升级各自独立计算后合并去重，按 `Level` 排序；
5. 用 `bpmn_group_resolver.go` 已有的"候选组展开"逻辑，把 `Role` + 对应 `OrgUnit` 解析成具体用户，而不是新写一套解析代码；
6. 输出结果写入本次请求各级 `ServiceRequestApproval.node`（JSON 快照字段已存在），保证审批完成后规则再调整也不影响历史留痕。

### 4.4 超时升级后台任务

新增一个扫描 `ServiceRequestApproval`（`status='pending' AND due_at < now()`，已有索引 `index.Fields("status","due_at")` 可直接用）的定时任务：

- 到期先标记提醒（不改状态）；
- 二次到期设置 `is_escalated=true`，升级对象取当前审批人所在 `OrgUnit`/`Department` 沿树向上一级的负责人（`Department.manager_id` 或 `OrgUnit` 对应分公司负责人角色），**不在规则表里单独配置"升级给谁"**，减少一套配置源。

### 4.5 BPMN 引擎的定位：不强行套多实例/DMN

鉴于 `nitram509/lib-bpmn-engine` 是 beta 版且不支持边界定时器/原生多实例/DMN（见 1.5 节），本设计的审批链解析和超时扫描**均在应用层实现**，不依赖 BPMN 引擎的原生特性——这与现有"会签"的实现思路一致（`CreateCounterSignTasks` 本身就是应用层模拟）。BPMN 引擎继续只承担它现在做得好的部分：ticket/change 域的条件网关审批。SR 域是否要接入 BPMN 桥接层（`bpmn_approval_bridge_service.go`）维持现状（同步展示待办），不作为本设计的强依赖。

## 5. 关键场景推演

沿用此前讨论的案例，标注每一步落到哪张表/哪个字段：

> 分公司A 采购部申请集团 ERP 系统只读权限，金额 8 万元/年。

1. 查 `ServiceCatalog`（该服务项）→ `approval_level` 对应的 `ApprovalChain`，其步骤中 `GroupControlled=true`（命中集团管控目录）。
2. 沿 `OrgUnit` 树核对 `AmountThreshold`：部门经理级 3 万 → 不覆盖；分公司IT负责人级 20 万 → 覆盖，金额维度到此为止。
3. 因 `GroupControlled=true`，无论金额是否已被覆盖，仍追加集团层节点（角色规则指向"集团IT分管领导"）。
4. 合并结果：采购部经理 → 分公司IT负责人 → 集团IT分管领导 → 集团安全团队（末级 `ApprovalType=parallel` 会签）。
5. 四条 `ServiceRequestApproval` 记录被创建，`node` 字段分别快照对应的角色/组织节点/规则版本；第四级会签沿用现有 `CreateCounterSignTasks` 的应用层实现模式。

## 7. 风险与待决策事项

- **BPMN 引擎选型风险**：`nitram509/lib-bpmn-engine` 为 beta 版，长期看若要给 ticket/change 域补边界定时器/DMN 能力，需要单独评估升级或替换引擎，本设计通过"SR 审批不依赖引擎原生能力"规避了这个风险，但不代表问题已解决。
- **两套实现收敛的数据迁移风险**：`/services/requests` 旧路径若仍有存量数据/调用方，收敛前需要单独盘点。
- **OrgUnit 与 Tenant 自引用的选型需要架构组确认**：方案 B 是本文档的推荐，但引入新表意味着一次数据模型评审，需要与既有 MSP/多租户路线图对齐（`docs/articles/09-multi-tenant-approval-practice.md` 描述的方向需要一并核对，避免后续再冲突）。
- **`ServiceCatalog.approval_level`/`approvers` 死字段**：本设计不再使用这两个字段（改用 `ApprovalChain`），建议后续单独评估是否废弃，避免同一份数据两处配置。
