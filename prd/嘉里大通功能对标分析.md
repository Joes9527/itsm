# 嘉里大通旧ITSM → 新ITSM 功能对标分析

> 基于旧ITSM 18个月数据（17,294条工单）与当前ITSM项目的数据结构、自定义表单能力对比

## 产品定位原则

**本项目定位为 Service Desk / Helpdesk 平台，而非云平台运维（Cloud Ops）工具。**

- 目标用户：企业 IT 服务台、一线支持人员、终端用户
- 核心场景：账号申请与生命周期管理、终端设备与办公支持、邮箱与协作服务、网络接入与远程访问、业务系统使用支持、故障报修与咨询
- 不做：K8S 集群扩缩容、DDL 执行、CI/CD 流水线、云资源申请等云平台运维场景（这些属于 Platform Engineering / Cloud Ops 域，不在 Service Desk 覆盖范围）

**所有功能设计、模板预设、分类体系均应围绕 Helpdesk 场景展开，剔除云运维预设。**

## 一、旧系统数据概况

- 数据量：17,294 条工单（2025-01 至 2026-06）
- 数据模型：**单表扁平结构**，20 个固定字段
- 来源渠道：邮件开单 30.7%（5,311条）、Web 14.3%、微信/QQ 3.3%
- 分类体系：65 个平铺的 `请求分类` + 13 个 `原因类型`
- 表单能力：**无**。所有业务信息混在 `描述` 自由文本字段中
- 核心数据质量问题：关键字段 30-50% 为空（优先级 48.8%、来源 49.4%、处理时长 46.8%、解决方案 48.1%）

## 二、字段级对标

### 已覆盖字段

| 旧字段 | 旧系统用法 | 新系统对应 |
|--------|-----------|-----------|
| 编号 | `SR20250102000001` | `ticket_number` |
| 标题 | 自由文本（7,392种值） | `title` |
| 状态 | 7种状态 | `status` |
| 优先级 | P0-P3 | `priority` |
| 创建/更新时间 | 时间戳 | `created_at` / `updated_at` |
| 请求人 | 纯文本姓名 | `requester_id` → User 实体 |
| 当前处理人 | 纯文本姓名 | `assignee_id` → User 实体 |
| 来源 | 7种渠道（邮件/Web/微信等） | `source` |
| 预计完成时间 | 日期 | `sla_resolution_deadline` |
| 描述 | 自由文本（含HTML邮件原文） | `description` |
| 解决方案 | 纯文本 | `resolution` + `resolution_category` |
| 请求分类 | 65个平铺值 | `TicketCategory` 树形结构（更强大） |
| 请求人组织架构 | 长路径字符串 | Department 树 + `department_id` 关联（不冗余存储） |

### 对标处理

| 旧字段 | 结论 |
|--------|------|
| **原因类型** | 由 Service Catalog 三级服务项覆盖，不新增字段 |
| **数量** | 作为自定义字段按模板配置 |
| **实施人** | 评估：是否加 `implementer_id` 或复用工作流任务指派 |
| **实施完成时间** | 复用 `resolved_at` |
| **响应时长 / 处理时长** | 实时计算（`first_response_at - created_at`），不需要存储字段 |
| **请求人组织架构** | 已通过 `department_id` 关联，不冗余快照 |

## 三、分类体系对标

### 旧系统：65 个平铺分类

```
KTMS系统(1660)    KAPP系统(922)     Ksmart系统(801)    KWMS系统_(223)
K365-结算(1139)   KBMS结算系统(293)  KOMS系统(122)      Ksmart Air(216)
企业应用系统-邮件系统(2133)          基础架构-网络(326)
本地系统-深圳支持中心-深圳(1315)      本地系统-深圳支持中心-成都(1237)
其他-其他(994)    ...
```

主要问题：
- 分类名称不规范（`KTMS系统` vs `KTMS系统_`）
- `本地系统-*` 按support中心命名，不反映实际服务内容
- `其他-其他` 占 5.7%

### 新系统：Service Catalog 三层结构

基于 `service-catalog-ownership-workshop-draft.xlsx`，已细化 4 个域：

| 一级分类 | 编码 | 二级分类数 | 三级服务项数 |
|----------|------|-----------|-------------|
| 账号与访问服务 | ACC | 4 | 9 |
| 终端与办公支持 | EUC | 5 | 17 |
| 邮箱与 Microsoft 365 协作服务 | COL | 6 | 19 |
| 网络与远程访问服务 | NET | 4 | 15 |

待细化域（标记在 Discussion Guide 中）：
- **业务系统支持** — 覆盖旧系统 58% 的工单量（KTMS/KAPP/Ksmart/KWMS等）
- **平台与基础设施服务**
- **安全与合规支持**
- **咨询与服务引导**

### 映射规则

| 旧分类 | → 新一级分类 | 说明 |
|--------|-------------|------|
| 企业应用系统-邮件系统 | 邮箱与M365协作服务 | 直接映射 |
| 基础架构-网络 | 网络与远程访问服务 | 直接映射 |
| 基础架构-堡垒机 | 账号与访问服务 > 特权与临时权限 | 直接映射 |
| 本地系统-*-* | 终端与办公支持 | 按服务内容再分发到具体三级服务项 |
| 其他-其他 | 咨询与服务引导 | 直接映射 |
| KTMS/KAPP/Ksmart/... | 业务系统支持 | 待该域细化后映射 |
| 企业应用系统-ITSM | 平台与基础设施服务 | 待细化 |

## 四、模板与自定义表单对标

### 旧系统：无表单体系

- 所有业务数据混在 `描述` 自由文本字段中
- 12,179 条（72%）纯自由文本，3,682 条（21%）HTML 邮件原文，1,433 条（8%）半结构化文本
- 无字段类型、无校验、无必填控制
- 标题作为隐式的"表单类型"（7,392种不同值）

### 新系统：三层动态表单

```
TicketTemplate（模板）
  ├── 绑定 TicketCategory
  ├── 绑定默认优先级
  ├── 绑定工作流
  └── FieldDefinition（自定义字段定义）
        ├── name: 字段key
        ├── label: 显示名
        ├── field_type: text | textarea | number | date | select | multiselect | boolean | file
        ├── required: 必填
        ├── options: [{label, value}]（select/multiselect）
        ├── sort_order: 排序
        └── config: 校验规则/默认值（预留）

FieldValue（字段值快照）
  ├── field_definition_id → FieldDefinition
  ├── field_name / field_label / sort_order: 提交时快照
  └── value: JSON 编码原始类型值
```

### 模板设计原则

- **按操作类型拆分模板**（账号申请、服务申请、故障报修...），不按系统拆分
- **"相关系统"字段** → 关联 CMDB 软件资产 CI，下拉列表由 CI 动态生成
- **批量处理** → 以附件形式提交，不建子表单/重复表格
- **业务系统软件资产** → KTMS/KAPP/Ksmart 等作为软件资产 CI 录入，可标记 `is_itsm_requestable`

### 模板设计示例

```
TicketTemplate "业务系统账号申请"
  ├── category: 业务系统支持 > 跨业务线通用 > 业务系统账号申请
  ├── default_priority: P3
  └── fields:
        ├── 目标系统    select  (选项来源：CMDB 软件资产 CI，is_itsm_requestable=true)
        ├── 操作        select  [新增 | 停用 | 权限修改 | 密码重置]
        ├── 账号姓名    text    (required)
        ├── 账号ID      text
        ├── 权限范围    textarea
        └── 用户申请表  file
```

## 五、邮件开单对标

### 旧系统

- 30.7% 工单（5,311条）通过邮件开单
- 邮件主题 → 标题，邮件正文（含HTML/CSS/签名） → 描述，发件人 → 请求人
- 无解析、无字段提取、无自动分类

### 新系统方案：Email Connector

```
┌─ Email Connector ────────────────────────────────────────┐
│                                                           │
│ 收信层：                                                  │
│   - IMAP 定时拉取 或 SMTP Webhook 接收                    │
│   - 发件人身份验证 + 垃圾过滤                              │
│                                                           │
│ 解析层：                                                  │
│   - 主题 → 标题                                          │
│   - HTML 清洗 → 纯文本 → description                      │
│   - 去除签名和引用历史                                    │
│   - LLM 辅助字段提取（P3，低置信度时人工复核）              │
│   - 附件自动挂载到工单                                    │
│                                                           │
│ 路由层：                                                  │
│   - 发件人域 → 匹配 User                                  │
│   - 主题关键词 → 推荐 Service Catalog 项                  │
│   - 无法识别 → 创建工单，归入"咨询与服务引导"              │
│                                                           │
│ 失败策略：                                                │
│   - 解析失败 → 原始邮件进 description                      │
│   - 发件人未知 → "来源=邮件" + 记录发件人邮箱              │
└───────────────────────────────────────────────────────────┘
```

实现优先级：

| 阶段 | 能力 | 说明 |
|------|------|------|
| **P0** | IMAP 拉取 + 原始邮件进 description | 最小可用——复刻旧系统能力 |
| **P1** | 发件人匹配 User + 附件自动挂载 | 提升数据质量 |
| **P2** | 主题规则匹配 Service Catalog | 减少人工分类 |
| **P3** | LLM 字段提取 + HTML 清洗 | 结构化数据填充到自定义字段 |

## 七、创建页改造方案（Phase 2 延伸）

### 当前问题

创建页工单类型来自两个不匹配的来源：
1. **静态预设** `ticket-type-presets.ts`（12种）：面向 Cloud Ops（K8S、DDL、GitLab等），与 Helpdesk 场景无关
2. **数据库模板** `ticket_templates`（4种）：Helpdesk 场景，但不完整

### 目标架构

**Service Catalog 驱动的 ITIL 标准流程：**

```
用户 → Service Catalog（选择服务项）
     → TicketTemplate + FieldDefinition（加载表单）
     → 填写 → 提交 → Service Request → Ticket
```

### 改造优先级

| 优先级 | 任务 | 说明 |
|--------|------|------|
| **P0** | 创建页改造 | Service Catalog 作为工单类型的主要来源，三级分类树驱动服务项选择 |
| **P1** | 静态预设降级 | 保留 Cloud Ops 预设但移至独立分类（如"运维操作"），不优先展示 |
| **P2** | Service Catalog 浏览页 | 独立的服务目录浏览/搜索页面，支持服务项详情和直接发起请求 |
| **P3** | 分类标签对齐 | 创建页分类标签从"技术支持/账户问题/系统故障"改为 ACC/EUC/COL/NET/BUS |
