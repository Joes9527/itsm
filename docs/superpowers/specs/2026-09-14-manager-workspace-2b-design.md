## 2. 主管页现状

入口为 `itsm-frontend/src/app/(main)/manager/live-board/page.tsx`，persona 配置将服务台/运维主管映射到此页面。源码中没有业务 API 调用：

- `MOCK_TEAM_MEMBERS` 固定四名成员、在线状态、在办数量及容量 8。
- 智能均衡派单仅定时弹出“派给最闲成员”成功消息。
- 固定 Exchange 故障告警、8 张相似工单、96% 置信度；点击合并后只弹“已合并并通知”的成功消息并隐藏告警。
- 今日进单/解决量、SLA 达成率、响应时间、待分配池均是固定数字。

这些不是实时运营证据。第一批必须移除假成功和虚构数据；不把现有函数名称当作已具备团队业务能力。

## 3. 实际契约盘点

| 能力 | 源码与运行证据 | 接入结论 |
| --- | --- | --- |
| 可见工单列表 | TicketApi.getTickets → GET /api/v1/tickets；ListTicketsRequest 支持 page/pageSize/status/priority/assigneeId。TicketService.ListTickets 将当前用户/角色转入仓储数据范围。当前开发 API 无筛选与 status=new 查询均 HTTP 200、code=0，返回 tickets/total/page/pageSize/totalPages | 可复用既有列表契约；total 只能表示同一筛选下当前授权可见数量 |
| 主管团队视野 | TicketService.isTicketDataScopeAllRole 仅允许 super_admin/sysadmin 全租户列表；sd_manager/ops_manager 当前仍是本人创建或分配范围 | 不能从主管 persona、菜单可见性或 user:read 推断团队权限；也不能前端去掉 assigneeId 后声称获得全团队 |
| 工单统计 | GET /api/v1/tickets/stats 已注册，要求 ticket:read，当前 API HTTP 200。Controller/GetTicketStats 仅传 tenantID；CountByStatus/FindOverdue 按租户查询，没有列表的 actor/行范围参数。服务中 highPriority 固定 0；逾期查询失败仅记录 warning 后仍返回 len(overdue) | 不直接作为主管团队 KPI 接入；需在所属统计边界修复授权一致性、字段语义和失败传播 |
| 团队工作负载 | TicketAssignmentController.GetTeamWorkload 和 service 方法存在，但 router/ 下未找到注册。Service 遍历租户所有 active 用户，不能等同服务台 L1/L2 组或“当前在线”；单人负载读取失败会跳过该用户 | 不新增一个路由就宣布可用；需要组范围、RBAC、租户/MSP、数据完整性与指标口径契约 |
| 单工单自动分配 | POST /api/v1/tickets/:id/auto-assign 已注册，权限 assignment_rule:update。SmartService.AutoAssign 接受单个 ticketID；target 非 nil 才更新 assignee。回执 AssignedTo 可空。规则列表 GET 已在当前 API 验证 200 | 不是批量均衡派单；HTTP 200 也不必然代表已分配。团队调度仍需明确目标集合、逐项授权、冲突/重试、审计及回执 |
| 重大事件 | POST /api/v1/incidents/:id/major-incident 已注册，对既有 Incident 执行重大事件操作；前端 IncidentDetail 已消费 | 不等于多张 Ticket 合并、自动创建 Incident、建立关系及全员通知。不能把统一关系或单事件升级接口当成批量合并命令 |
| AI 聚类及告警 | 当前主管页的告警和置信度均固定；本轮未确认能返回授权范围内聚类结果及可审计操作建议的端到端契约 | 不保留伪造结果，不按关键词在前端自建聚类器 |

## 5. 推荐的 2B-1 具体范围

将页面明确命名为“主管工单概览”，注明“仅显示当前账号授权可见的工单”。保留角色入口，展示真实分页列表、当前筛选返回的 total、状态和优先级筛选、刷新及进入已有工单详情的链接。

- 使用 TicketApi.getTickets；不传猜测的团队 ID，不遍历用户拼装“团队列表”。不增加全局缓存或第二个统计服务。
- 当前筛选数量直接来自同一次响应的 total，不取当前页长度，不叠加多次查询估算 KPI。只呈现实际状态值，不将 pending 称为“待用户回复”、new 称为“未分配”。
- 进入 `/tickets/<WorkItem ID>` 复用已有详情；本批无需再次构建一套嵌入式处理 UI。
- 删除固定 KPI、成员、容量、在线标签、AI 告警和假成功回调。保留“团队负载”“智能均衡派单”“重大事件合并”能力说明，按钮禁用且原因可见；不显示技术实现名 TeamWorkloadResolver。
- 会话/租户/读取权限变化清列表和计数；首次失败与正常空列表分开，同一范围刷新失败明确保留上次结果；最终拒绝清内容；换筛选或页码时禁止迟到响应恢复旧结果。
- 权限门控消费会话明确授权；persona 仅决定入口。主管可见范围与工程师一样窄时如实展示，不放宽后端策略。
- UI 使用已有 Ant Design、布局和主题 token；本批不全仓迁移样式。

生产改动预计仅主管路由及其局部组件/hook、已有 API 参数类型（如需）；测试放对应相邻 __tests__ 和 tests/e2e/flows/。不把只对个人分配有语义的 useAssignedTickets 改成参数复杂的通用队列框架。

## 6. 后续领域待办

1. **统计可信性**：复用现有业务数据范围策略，统计与列表对同一 actor/租户保持一致；明确 highPriority、pending、逾期、时间窗、分母与错误传播。修改原服务/仓储，不建立平行聚合接口掩盖原问题。
2. **团队负载**：先定义主管管理的组集合、MSP 边界、在办状态和容量来源；账户 active 不能冒充在线，用户数不能冒充在岗数。缺失成员或查询失败要可观察。
3. **智能派单**：明确预览/确认的记录集合与范围，采用既有领域分配策略；逐项回执、当前权限、版本冲突、操作重放和审计必须明确。无匹配目标不能报告“已派单”。
4. **重大事件工作流**：确认是创建/升级 Incident 并关联源记录，还是领域另有受控合并语义；保留原记录及历史，不通过修改 recordClass 转换。广播通知属于单独明确授权且可审计的副作用。
5. **AI 聚类**：结果必须包含真实来源、租户/权限过滤、置信度及模型等必要元数据；缺少契约时保持未接入。

本次只登记这些依赖，不授权迁移、调整主管数据范围或执行批量派单/通知。
