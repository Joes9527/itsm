# 工程师工作台 2A：真实队列与既有处理能力复用

- 日期：2026-09-14
- 状态：implemented（仅 2A；已按方案 1 完成并验收）
- 设计基线：`aad7662b`，包含 UI 工作台 1A；主线 `a25e108d` 尚未包含 1A。
- 范围来源：[UI 工作台补齐设计](2026-09-14-ui-workbench-completion-design.md) 第二阶段。
- 实施方式：沿用用户选择的当前任务内顺序执行，每项完成后独立审查。实施使用独立功能分支；若 1A 尚未合并，明确以 1A 为前置提交，交付时先集成 1A。

## 1. 为什么先做 2A

1B 的主线集成和运行环境端点均不满足准入，证据维护在上游设计。2A 不依赖关系写入，可独立消除角色默认工作台的虚假操作。

现有 `itsm-frontend/src/app/(main)/workspace/tickets/page.tsx` 使用两条 MOCK_TICKETS、固定队列数量和申请人画像。回复、转派和结单只弹成功消息；AI 摘要通过定时器返回固定文字，回复草稿也固定为许可证开通内容。不能把这些提示当成业务执行证据。

已核查的真实能力：

| 能力 | 证据与限制 |
| --- | --- |
| 分给我的队列 | TicketApi.getTickets → GET /api/v1/tickets；后端 ListTicketsRequest 接受 assigneeId，TicketService.ListTickets 传入仓储过滤，并施加当前用户行范围 |
| 当前环境读取 | 登录后 GET /api/v1/tickets?page=1&pageSize=1&assigneeId=1 返回 HTTP 200、code=0，data 含 tickets/total/page/pageSize/totalPages；这是管理员烟测，不能代替普通工程师权限验收 |
| 详情处理 | /tickets/[ticketId] 当前直接使用 TicketDetail；该组件已有可选 id 属性，可以按所选真实 WorkItem ID 复用 |
| 评论与附件 | 1A 已恢复共享组件、错误状态、身份保护及真实写入；2A 复用该处理路径 |
| 其他原型队列 | DTO 没有“30 分钟内超时”的区间过滤；pending 不等于“待用户回复”；未核验具备 L1 组范围的未分配池契约。不能用当前一页数据推算这些队列及总数 |

## 2. 方案比较和推荐

1. **推荐：真实个人队列 + 复用 TicketDetail。** 保留工作台内选单与处理体验，评论、附件、分配及既有动作复用 1A 路径，避免新建第二套状态机与写入逻辑。代价是需调整容器布局，并验证嵌入模式下的选中记录和权限状态。
2. 真实队列点击后跳转完整详情页。改动最少，但失去工作台连续切换处理的体验，可作为产品主动简化时的选择。
3. 保留现有原型三栏并逐个重写操作。更贴近原型，但复制评论、分配、生命周期、AI 接线和身份保护，维护成本高，不推荐。

本设计建议方案 1，先交付“分给我的”完整读取与处理流程。2A 不宣称所有角色工作台或所有专业生命周期动作完成。

## 3. 页面、数据与操作边界

- 左侧从当前登录用户 ID 查询“分给我的”，采用服务端分页。人数身份未就绪时不发无 assigneeId 的查询；不得自动改查全租户。
- 数量只显示相同查询返回的 total；选中记录使用数值 WorkItem ID，ticketNumber 仅用于显示。
- 提供分页和刷新。首次成功选择本页第一条；换页仅选择新页中的记录；刷新后记录已移出队列则清除旧选择，并选取本页首条或显示空状态。禁止旧响应恢复先前选择。
- 右侧复用 `<TicketDetail id={String(selectedId)} />`，保留其既有评论、附件、分配、服务申请、审批和权限门控。操作后用户可以刷新队列；本批不引入轮询、全局缓存或第二份统计。
- 若嵌入需要控制返回入口，只增加真实使用的可选展示参数，默认保持 /tickets/[ticketId] 行为；不复制 TicketDetail，不改造其业务所有权。
- 旧页面假成功回调、固定工单、画像、倒计时、摘要、AI 回复及相似方案原型入口全部移除。共享组件若仍被其他页面使用，保留文件，本任务不进行全仓清理。
- 未核验的三种队列显示禁用及简短原因，不显示固定数量：“未分配池：待接入分组队列”“即将超时：待接入 SLA 队列”“待用户回复：待明确状态契约”。不能将 pending 偷换为待用户回复。
- 此页不另造“完成并结单”。既有详情动作只有后端确认后才能报告成功；专业域不支持的动作维持其所属详情既有边界，不通过通用 status 写入强行补齐。
- 本批不重写主管、管理层、ChatBI，不接入新的 AI 提供方，不扩大工单或人员可读范围，不执行数据库迁移。

## 4. 授权、并发与错误

- 会话用户、用户租户、当前工作租户和读取权限变更时，使队列请求失效，立即卸载所选详情并清除队列、计数及错误状态。persona 只决定页面入口，不授予权限。
- 查询通过既有安全 httpClient 和 TicketApi，鉴权/CSRF遵循共享客户端策略。队列范围仍由后端校验，前端 assigneeId 不是权限边界。
- 首次网络失败显示错误和重试；同一身份同一页刷新失败可保留上次结果并注明刷新失败。切换页时不将旧页结果伪装成新页；最终 401/403 清除内容及所选详情。
- 新请求、身份切换、权限撤销和卸载均使旧请求失效；A 请求晚于 B 返回时不得覆盖 B。
- 详情继续使用 1A 的上下文保护。组合验收必须覆盖选单 A→B 时草稿和迟到响应不串单，不能只测试队列 hook。

## 6. 验收与执行边界

1. 请求必须包含当前用户 assigneeId 与服务端分页参数；无用户身份/读取权限不请求。真实空列表与错误分别呈现。
2. 队列总数来自响应；分页、刷新、记录移出队列、最终拒绝和迟到响应都有行为测试。
3. 组合测试使用真实 TicketDetail 或其实际共享评论/附件消费者，验证选择不同 WorkItem ID 与草稿清理。不得将所有业务面板 mock 为 null 后宣称集成通过。
4. 真实浏览器以独有 ENGINEER-WORKSPACE-* 测试记录验证：登录→个人队列→选单→评论→刷新后持久化；分配给其他测试处理人后刷新应移出原队列。测试账号选择及受影响标记记录在实施时固定，不修改既有业务工单。
5. 补普通工程师与无权限用户验收；若当前环境缺相应账号/权限配置，则明确未验证，不能用管理员通过代替。用户已允许使用当前开发环境，无需再次询问环境选择；创建账号或调整权限若成为必要条件，应先登记具体影响。
6. 桌面与 390px、light/dark 检查：窄屏队列在上、详情在下，无新增整页横向溢出，键盘可选择工单，未支持队列的原因可见。
7. 运行相邻 Jest、TypeScript、lint、生产构建和相关 E2E；涉及共享组件再运行 1A 回归。全局门禁按实际最终影响运行并记录，不能用旧分支结果代替。
8. 沿用每项实施后独立审查；交付注明前端提交、真实后端版本或二进制指纹、保留测试数据与未覆盖项。流程中测试工单不可删除时，尊重后端限制。

## 7. 已确认的产品范围

用户已批准第 2 节方案 1：本批只让“分给我的”成为真实可处理的工作台，其他队列明确禁用，主管及管理层留作后续独立设计。编写具体实施计划并按用户已选择的顺序执行方式推进，不重新询问执行模式。
