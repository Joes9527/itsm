## 1. 定位与依据

本设计为已进行中的 WorkItem 重构提供后续开发契约，覆盖 Incident、Problem、Change，以及共享身份、分派、协作、流程、通知和 SLA；generic、Requested Item 纳入公共能力回归。

权威模型仍是 [AGENTS.md](../../../AGENTS.md)、[原 WorkItem 设计](2026-08-26-unified-work-item-model-design.md)与 [accepted 收敛设计](2026-09-09-workitem-convergence-design.md)。本文件细化下一批工作，不取代专业生命周期、历史免迁移或切换门禁。决策过程、行业比较入口、已确认与延期范围见[开发输入记录](2026-09-11-workitem-convergence-development-input.md)；缺陷和反例见[独立评审](../../review/2026-09-11-workitem-convergence-review-report.md)。Incident 特有行为以[分配子决策](2026-09-11-workitem-incident-assignment-convergence-design.md)为准。

维护者已确认顺序：后端契约 → 页面操作 → 跨域验收与退役门禁。实施任务见[后续总计划](../plans/2026-09-11-workitem-next-stage.md)；原 A/B/C 计划需按代码现状更新，不重新执行已完成成果，也不能仅按原勾选状态判断完成。

## 2. 方案与边界

| 方案 | 收益与代价 | 选择 |
|---|---|---|
| 统一契约，复用现有服务与组件，分批完成所有入口 | 保留已有成果；每批能审查事务、权限与真实行为，但需完整入口盘点 | 采用；与既有 accepted 方案及本轮批次决定一致 |
| 只修 R1–R7 反例 | 短期改动少；不能证明其他入口和页面已收敛 | 不作为完成范围 |
| 重建通用状态机与统一万能详情页 | 表面统一，扩大重写范围并侵入专业规则 | 不采用 |

继续以 tickets 保存 WorkItem 公共事实，专业扩展不复制负责人、状态、标题、版本等字段。保留专业 URL/API，复用公共详情组件；不同 API 可以调用同一专业动作，不能保留两套规则或双写实现。不增加新的审批引擎、跨域万能服务、关系存储、SLA 计时器或兼容层。

本轮不增加 Change 多 WorkOrder 拆分与独立派工（BL-CHG-WO-01），不修改首次响应与考核口径（BL-RESP-01），不扩展 Catalog Task 或多条目 Request Header。已有 BPMN 任务与 SLA 周期正确性仍在范围内。

## 3. 批次一：后端契约

### 3.1 所有者与调用关系

| 单元 | 职责及现有承载位置 | 依赖与边界 |
|---|---|---|
| HTTP、BPMN、自动化入口 | 解析输入、建立可信上下文、调用动作 | 不直接更新专业状态，不自行推定租户或审批权限 |
| IncidentService / handlers/problem / handlers/change | 校验专业前提，编排同一事务 | 按当前模块风格改造，不另建平行 endpoint；不跨域直接调用 repository 实现 |
| handlers/shared/workitemmutation | Meta、版本、摘要、回执等共同协议 | 复用现有能力；不接管各专业状态机 |
| WorkItem 基础记录与专业扩展 | 公共字段与专业事实的唯一持久化位置 | 创建、更新、必需审计和事件遵守事务边界 |
| 现有 Outbox 与通知消费者 | 提交后可靠通知、结果传递 | 不代替领域动作；每次投递重新验证所需授权 |

实施前形成操作入口清单：操作、调用方、领域所有者、目标身份、实际写入、版本来源、回执、旧路径、测试。覆盖专业 API、通用字段编辑、调查模块、流程和自动化；只读 DTO 投影不视为重复存储。每个被替换操作在本批完成时只保留一个权威执行路径。

### 3.2 责任调整

| 场景 | 业务结果 |
|---|---|
| Incident new 首次分配 | 进入 assigned；按已确认子决策执行 |
| Incident 合法非终态转派 | 保留当前进度；允许 assigned 状态中的再次转派 |
| Incident 开始处理 | 可直接开始，不强制先 acknowledge；不因该动作隐式补记首次响应 |
| Change 仅更换负责人 | 保留阶段、审批结果、审批任务人员和实施任务执行人；负责人承担全程协调 |
| Problem 仅更换负责人 | 保留调查阶段、RCA、方案及验证证据；内容或方案变化时由专业规则判断证据有效性 |
| 已结束记录或其他非法状态的分派 | 按既有专业规则拒绝；不通过转派暗中重开 |

每次转派原因必填，去除首尾空白后不得为空。系统记录实际操作人、时间、原负责人、新负责人、原因及来源。BPMN/自动化同样提供可追溯触发原因，不用固定占位文本绕过要求。此决定针对实际转派，不额外规定首次分配必须填写原因；沿用已有首次分配输入要求。处理组单独调整、清空负责人等既有操作不能借此获得新权限，仍按现有专业规则核查。

不新增交接审批、独立交接表或必须接单的新步骤。转派记录进入现有审计/时间线。单纯人员变化不让验证证据失效，也不赋予审批身份；同一人可承担多种职责，但权限与任务归属分别验证。

### 3.3 请求、事务与重放

复用现有命令协议。动作应具备目标身份、目标负责人及原因等业务输入，调用者观察到的 expectedVersion，以及 operationId；actor、tenant、source 由已认证服务上下文建立，不信任表单自报值。专业 ID 可作为专业入口参数，但必须验证并解析其真实 WorkItem，不能假定两个 ID 相等。

一次动作的执行顺序：

1. 验证当前身份、域权限、租户/行范围、目标人员资格与参与条件。
2. 在一致的事务快照中读取权威记录，检查已有操作回执；同键同内容返回已提交结果，同键不同内容明确拒绝。重放仍需当前授权，不能靠旧回执绕过撤权。
3. 未命中回执时比较调用者观察版本，验证状态、原因及专业前提；不能用刚读取的版本替换请求版本。
4. 原子保存公共/专业变更、版本、必需审计/时间线事实、回执与可靠事件；任一必需写入失败全部回滚。
5. 提交后由现有消费者处理外部通知，通知失败不回滚已提交业务动作。

请求摘要应包含影响业务结果的目标、动作、版本、负责人和原因。沿用既有回执唯一范围，不另建第二套幂等存储。网络重试保持同一逻辑请求的操作键；用户查看新版本并修改意图后，作为新请求提交。工作流冲突可重新读取和校验后决定后续，不能无条件覆盖重试。

错误沿用项目现有响应格式并区分：输入不合法、当前权限不足、专业条件未满足、版本冲突、同键内容冲突、暂时基础设施失败。拒绝不得半写；权限错误不得泄漏不可见关联记录。实施计划核对实际 HTTP 映射，不因本设计增加平行错误协议。

### 3.4 BPMN 身份与配置：R1/R2

身份统一为 recordClass、WorkItem ID 及二者构成的 businessKey；实例、任务、审批快照和保留变量一致。公共身份构造/验证沿用当前实现，启动请求的用户变量含保留键时明确拒绝，不允许合并时覆盖权威值。

同时覆盖真实配置链路：维护中的默认 JSON、嵌入配置、种子加载、流程绑定创建/更新、发布校验、触发与回调。种子直接写 Ent 的入口也须使用一致校验，不能只修改 API 或未实际加载的配置。规范词表从既有身份定义取得，不新增另一份别名表。

历史检测器识别旧词表属于预检职责，不是运行兼容；Release 保持既有显式边界。旧实例、旧审批快照和历史变量不批量转换，未排空依赖阻断切换。

### 3.5 通知与可靠性：R3–R6

保留现有消费者和 Outbox。投递必须使用真实运行注入的客户端与客户租户上下文；不能用管理员客户端的测试通过证明 Tenant 客户端可运行。

MSP 场景复用 authorization 与身份解析边界：提供方人员身份的窄范围查询，与客户租户内 WorkItem 读写分开。不得把整个通知消费者切到管理员权限。校验当前账号、域权限、有效租户/MSP 服务范围、关联双方可见性，以及接收人是否仍有资格读取通知内容。既有端口不足时只扩展所需身份/授权查询，不新增宽泛跨租户读接口。

| 投递情况 | 结果 |
|---|---|
| 权威查询成功证明人员无效、授权撤销或关系不再有效 | 明确 blocked，并提供不泄漏数据的可观测原因 |
| 数据库不可用、查询超时等暂时错误 | 返回可重试失败，沿用 worker 的退避及重试上限 |
| 未知错误 | 不伪装成确定性无权限；保留失败分类并按既有重试/最终失败机制处理 |
| 已成功投递的相同事件/目标 | 幂等返回，不产生重复通知 |

通知中区分“产生变化的记录”和“接收方所在的关联记录”，引用正确对象，避免通知收件人其自身发生了对端变化。重试期间若授权变化，使用当前授权重新判断。跨域结果默认提示后续验证，不自动完成 Problem 或关闭 Incident。

## 4. 批次二：页面操作与公共体验

三域已使用 WorkItem Shell；评论、附件、历史和关系已传 WorkItem ID。这部分保留，真实权限和持久化效果另行验证。当前公共类型缺少 version，SLA 类型缺少周期历史投影；这些是已确认静态缺口，不代表其他链路已验收。

### 4.1 详情与动作契约

专业详情提供明确的专业 ID、workItemId、权威 number、version、公共字段、专业字段和后端 actions。公共字段从 WorkItem 组装；专业 ID 不作 WorkItem ID 或编号兜底。缺少必需身份时页面显示明确加载错误，不以猜测值提交。

公共 Shell 复用分派与协作交互，专业 Panel 保留专业内容和动作输入；可以通过现有回调交给专业 API 执行。后端返回动作是否可用及原因，前端展示原因但不重建权限/状态机。仅有公共按钮不表示动作可用，按钮隐藏也不构成后端授权。

转派交互展示当前负责人、选择目标人员、填写原因；成功后使用权威结果刷新版本、负责人及时间线。客户端可阻止空白提交，但后端同样验证。首次分配与转派标签按权威数据区分，不为所有专业域套用 Incident 的 assigned 规则。

### 4.2 冲突、失败与协作

409 冲突保留用户输入、说明记录已变化，重新加载权威数据供用户确认后提交；不能静默覆盖或自动换版本重发。同键重放不重复时间线、SLA 周期或通知。一般服务失败保留输入并显示失败；无权限时停止操作，不暴露不可见数据。

评论、附件、历史和关系统一挂到 WorkItem 身份；沿用现有公开/内部可见性规则，不以本设计扩大请求人可见范围。核查专业 Panel 是否还有重复公共读写，存在实际重复才删除。覆盖加载、空、错误、无权限、冲突和成功状态。

### 4.3 SLA

从后端展示已应用策略、当前周期截止时间与完成事实，以及已保留的历史周期结果。合法重开后显示新周期，原创建时间及旧周期违约结果保留。页面不再次匹配策略或自建计时权威；具体计时规则引用 accepted 设计第 7 节。

BL-RESP-01 仅延期响应考核语义调整；不改变现有 acknowledge 对首次响应记录的行为，也不把 assign/start 自动视为首次响应。无需 SLA 的记录明确展示未应用；应有策略但缺失时显示配置错误，不能显示为未超时。

## 5. 批次三：跨域验收与退役门禁

### 5.1 验收场景

| 场景 | 必须证明 |
|---|---|
| 三域转派及不同入口 | 原因必填；状态/审批/证据遵守各域约定；HTTP、BPMN、自动化结果一致 |
| 缺原因、陈旧版本、审计失败 | 变更被拒绝或回滚，无部分更新 |
| 同键重复、同键改内容、撤权后重放 | 不重复副作用；冲突与当前授权正确执行 |
| Incident 使用 workaround 恢复 | 可独立解决；关联 Problem 保持原状态 |
| Problem 只有 workaround 或未验证永久方案 | 拒绝解决，保留已有事实 |
| Change 失败/回滚、成功但根因验证失败 | 保留真实 Change 结果；不自动解决 Problem 或重开 Incident |
| 必需 Change 成功且永久方案验证通过 | 经显式 Problem 动作才能解决 |
| 合法重开与重复重开 | 当前周期归零，旧结果和 createdAt 保留，重放不重复建周期 |
| 保留变量覆盖与真实默认配置加载 | 覆盖被拒绝，配置不重新引入旧流程身份 |
| MSP 实际运行客户端、撤权、暂时查询失败 | 合法通知可达；越权 blocked；暂时失败可重试；正文指向正确记录 |
| generic / Requested Item | 创建、权限、分派、评论、附件和已有审批流程无回归 |
| 专业 ID 与 WorkItem ID 不相等 | 页面展示、动作、协作与流程仍引用正确身份 |

单元测试验证专业规则与错误分类；PostgreSQL 测试验证事务、回执竞争、RLS 及约束；前端契约/组件测试验证实际页面映射和输入保留；隔离浏览器 E2E 验证上述跨域旅程，并查询持久化结果，不只断言提示消息。测试使用实际运行客户端组合，不以管理员权限替代 RLS 验收。

三个已知后端失败分别归因并修复或取得可解释基线：迁移版本数量断言、冻结 Incident 分派流程、旧 intake category 请求体。阶段子集通过不替代全部必需检查，不能将本重构引入的断言漂移一律称为历史失败。

### 5.2 切换和结构删除

严格继承 accepted 设计第 10 节：隔离演练 → 目标只读盘点 → 排空旧依赖 → 验证可恢复备份 → 暂停相关写入/消费者 → 新结构与完整性核对 → 唯一新路径 → 完整验收 → 恢复写入并观察 → 再核对证据 → 删除清单内旧结构 → 健康检查。

观察期间旧代码读写已经退出；旧表暂留只服务恢复门禁，不作为双读来源。物理删除依赖观察验收，应用旧路径的退出不得拖到未来无期限 backlog。旧依赖未排空、备份未验证、保留记录不一致或仍有未解释失败时阻断，不自动取消流程、清洗历史或猜测映射。

实施计划必须列出实际表/列/约束、消费者、迁移注册、恢复方案和环境准入。发生新写入后恢复要协调数据库与应用版本，说明新增数据补偿范围。本设计及后续代码完成均不等于授权执行共享环境删除。
