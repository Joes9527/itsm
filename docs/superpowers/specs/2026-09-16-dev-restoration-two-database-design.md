# 原 Dev 恢复与双数据库收敛设计

- 状态：accepted；维护者于2026-09-16确认本书面设计。方案A及四阶段执行边界生效，实际操作按唯一执行清单与阶段门槛推进。维护者已否决新增PG容器，指定本次采用同数据库、不同schema方向；具体克隆准入与隔离实施方案仍待完成，见下文。
- 日期：2026-09-16。本文是设计，不是实际执行回执。
- 原因与证据：[Dev031与主干047分离分析](../../review/2026-09-16-dev-schema-divergence-report.md)。任务状态只维护在[唯一清单](../plans/2026-09-15-migration-validation-ledger.md)，运行规则见[环境合同](../../development-environment.md)。

## 1. 目标与选型

采用方案A：保留原Dev并前向升级，恢复开发后，从验收后的Dev建立可追溯克隆，复用旧ITSM迁移成果完成验证。没有选择副本接替Dev或新空库重建身份配置，以减少身份、关联及连接迁移风险。047是当前选定代码的结构要求，不是数据库名称；后续代码改变必须重新核对兼容性。

最终只保留Dev和迁移验证两个长期ITSM数据目标；按维护者最新指示，它们使用同一数据库内的不同schema，不再等同两个物理数据库：

| 角色 | 数据库 | 运行方式 |
| --- | --- | --- |
| 日常Dev | `itsm-postgres-dev / itsm_config_baseline_20260908` | 3010→8080日常使用，前向升级并保留业务配置 |
| 迁移验证克隆 | 同一ITSM数据库内的独立验证schema（尚未创建，名称在实施方案固定） | 从已验收Dev快照恢复；验证窗口使用相同前后端版本，结束后切回Dev |

### 部署方向纠正（2026-09-16）

维护者已否决新增常驻PostgreSQL容器。本次方向为：复用现有PG实例和ITSM数据库，Dev保留当前schema，迁移验证放入独立schema；原“同实例不同库名”方案被此方向取代。schema是数据库内的命名空间，此处用于分开两套表及数据。具体schema名称、角色权限和克隆准入方案尚未实施。

长期ITSM/KAF整合沿用[单PG实例、双逻辑库计划](../plans/2026-09-14-itsm-kaf-task-3-pg-consolidation.md)：ITSM与KAF共用一个PG实例，保持各自逻辑数据库和领域所有权。本次ITSM内Dev/验证schema划分不等于把KAF表搬入ITSM库，也不代表实例合并已执行。

现有配置支持`DB_SCHEMA`，但准备回执校验同时绑定数据库与schema；复制到另一schema不能直接通过准入。后续须设计可审计的克隆来源/目标证明，保留原SQL、校验和与历史回执；验证受限角色不能跨schema访问、连接缺失时不能回落到Dev、迁移账本/序列/函数/触发器/RLS及消费者确实隔离。不得把支持schema参数等同于已支持完整克隆。

Dev与验证独立设置运行/系统/检查权限、Redis空间、附件空间、会话和后台执行配置，不共用待处理队列或外发状态。3010→8080使用同一选定代码，每次只加载一个明确目标的完整profile。克隆保留新系统Dev测试记录不等于导入旧ITSM ticket。此前“独立PG保留内部库名”的建议已撤回，不再等待该选择。

不建立自动双向同步。后续重新克隆必须先保全验证结果和增量配置，再显式刷新；日常开发不等待迁移验收全部完成。KAF、Langfuse、PostgreSQL系统库及其它产品数据不在本次清理范围。

## 2. 数据与配置边界

| 类别 | 处置 |
| --- | --- |
| 用户、组织、租户、角色、权限、密码及关联 | 必须保留；升级前后验证稳定身份和关联，不重置凭据或权限 |
| 目录、分类、字段、SLA、流程定义与自定义配置 | 必须保留业务内容和可追溯来源；适配新模型的字段变化逐项记录，不能用seed整套覆盖 |
| 废弃测试业务数据 | 可整理或重建；实例7–10已确认废弃，其它先分类并列具名清单。终止活动流程使用领域路径，关联清理经验证后执行，保留必要操作证据 |
| 19条旧流程绑定 | 用途明确的逐项适配规范类型并验证路由，之后停用旧绑定；保留修改前配置及变更记录，不按字符串无差别替换 |
| 824与6条云业务绑定 | 保留定义和配置，停用并标记待适配；用途确认后再恢复，不凭名称推导目标类，不列为此次已恢复能力 |
| 旧ITSM ticket、审批、评论、附件、历史流程 | 不导入；复用已确认基础/配置数据范围及既有工具 |

保护配置不要求保留过时的启用状态，但不允许丢失自定义内容。若其依赖阻塞必要开发路径，应报告具体缺口，不伪造默认绑定或成功结果。

## 3. 四阶段执行与验收门槛

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1 固定范围 | 固定源码/制品、两库目标、数据与配置变更清单、备份恢复证据、运行profile、具名清理候选与消费者 | 目标身份明确，备份可恢复；身份/业务配置保留基线可核对；所有写入有明确范围 |
| 2 恢复Dev | 在副本验证最终变更包；维护窗口停止相关写入/消费者，升级原Dev、整理已识别测试数据、适配绑定，恢复3010→8080 | 结构及权限检查通过；身份与业务配置保全；readiness、登录、租户/权限及通用工单、变更、服务请求代表性UI路径通过。未适配能力明确列出 |
| 3 建立验证克隆 | 从验收Dev一致性快照恢复，保存来源、时间、摘要及附件边界；集成复用现有Toolkit，比较并应用获准迁移差异 | 克隆身份和关联完整，两个profile隔离；旧数据在新模型上的代表性UI路径可用；验证结束入口回Dev |
| 4 清理收尾 | 保全成果及证据后归档删除其余无用途ITSM业务/测试库、专属容器/卷与旧启动资源；同步当前入口 | 实际盘点只剩两个长期ITSM业务库；临时预演资源退出；备份作为文件保留；无遗留消费者或文档指向删除对象 |

结构迁移复用已预演的P037与普通032–036、039–047依赖链，不单独硬跑047，不修改历史SQL/校验和，不使用Ent补表，不执行独立R038退休。所需临时迁移权限限定操作窗口并验证撤销；应用身份不升级为owner。清理业务测试数据和旧环境不等于批准退休旧结构。

19条绑定调整、旧流程终止与最终配置验收要在最终副本验证中覆盖；已有结构预演证据继续复用，只对变化和未覆盖项补验。共享环境只有一个写入负责人，其他Agent可做独立只读审查。

## 4. 迁移成果与清理策略

既有五批384对象证据保留，不重新设计已采纳映射，也不冒充新克隆验收。按租户与稳定业务键比较新克隆：一致对象跳过，缺失/冲突列差异，再复用适用工具处理。Toolkit的users/departments能力不替代配置批次工具；旧收据不得复制成新库执行收据，示例/占位对象不自动补入。

`itsm_ga_ready`、`gb_replay_review`及历史对照库先保全成果，完成目标库差异核验后退出。删除清单必须具名列出实例、库、专属容器/卷、消费者、备份与恢复证明，逐项复核后按已确认范围执行；有活跃依赖的对象先迁移依赖，不能直接删。禁止按名称通配清库或删除共享PG容器/卷。异常发现范围外消费者时暂停该对象清理。

“只剩两个库”的验收覆盖维护中的WSL ITSM实例及历史ITSM专用实例；已停止容器中可恢复的旧数据库也须归档退出，不能仅停止后隐藏计数。备份文件不计为在线业务库，PG系统库不计入业务库数量。

## 5. 失败处理与恢复

- 执行前固定可恢复基线，包括数据库、角色配置及附件覆盖；任一关键保留检查失败，停止后续变更。
- 未开放开发写入时失败：在维护窗口按验证过的恢复步骤恢复原数据和匹配运行配置；禁止让当前代码继续连接不兼容结构。必要旧制品仅作为有明确退出条件的临时恢复，不作为长期开发方案。
- 开放开发后失败：优先前向修复；不得直接恢复旧备份覆盖新增业务数据。确需恢复时先保全新增数据并明确补偿方案。
- 克隆验证失败：保留证据，恢复Dev完整profile；不让验证故障长期占用开发入口。
- 新目标和恢复证据未通过前，不删除旧成果库和备份；历史库删除失败记录具体对象，不把阶段4标为完成。

## 6. 执行透明度与token预算

只维护一份执行清单，使用上述四阶段；每阶段汇报“完成、验证、阻塞、下一步”。默认简报，原始日志与敏感数据留私有证据目录。已有证据在源码、目标及条件未变化时复用；出现变更、失败或明确覆盖缺口才追加检查，不机械重跑全套。

串行处理共享写入，独立审查按必要风险边界安排，不启动重复调查。书面设计已确认，执行步骤维护在唯一清单；阶段门槛满足后开始相应环境操作；本文件提交不代表已执行升级、停用、克隆或删除。
