## 1. 目标与选型

采用方案A：保留原Dev并前向升级，恢复开发后，从验收后的Dev建立可追溯克隆，复用旧ITSM迁移成果完成验证。没有选择副本接替Dev或新空库重建身份配置，以减少身份、关联及连接迁移风险。047是当前选定代码的结构要求，不是数据库名称；后续代码改变必须重新核对兼容性。

最终只保留Dev和迁移验证两个长期ITSM数据目标；按维护者最新指示，它们使用同一数据库内的不同schema，不再等同两个物理数据库：

| 角色 | 数据库 | 运行方式 |
| --- | --- | --- |
| 日常Dev | `itsm-postgres-dev / itsm_config_baseline_20260908` | 3010→8080日常使用，前向升级并保留业务配置 |
| 迁移验证克隆 | 同一ITSM数据库内的独立验证schema（尚未创建，名称在实施方案固定） | 从已验收Dev快照恢复；验证窗口使用相同前后端版本，结束后切回Dev |

### 部署方向纠正（2026-09-16）

维护者已否决新增常驻PostgreSQL容器。本次方向为：复用现有PG实例和ITSM数据库，Dev保留当前schema，迁移验证放入独立schema；原“同实例不同库名”方案被此方向取代。schema是数据库内的命名空间，此处用于分开两套表及数据。具体schema名称、角色权限和克隆准入方案尚未实施。

长期ITSM/KAF整合沿用[单PG实例、双逻辑库计划](../plans/2026-09-14-itsm-kaf-task-3-pg-consolidation.md)：ITSM与KAF共用一个PG实例，保持各自逻辑数据库和领域所有权。本次ITSM内Dev/验证schema划分不等于把KAF表搬入ITSM库，也不代表实例合并已执行。

现有配置支持`DB_SCHEMA`，但准备回执校验同时绑定数据库与schema；复制到另一schema不能直接通过准入。后续须设计可审计的克隆来源/目标证明，保留原SQL、校验和与历史回执；验证受限角色不能跨schema访问、连接缺失时不能回落到Dev、迁移账本/序列/函数/触发器/RLS及消费者确实隔离。不得把支持schema参数等同于已支持完整克隆。

Dev与验证独立设置运行/系统/检查权限、Redis空间、附件空间、会话和后台执行配置，不共用待处理队列或外发状态。3010→8080使用同一选定代码，每次只加载一个明确目标的完整profile。克隆保留新系统Dev测试记录不等于导入旧ITSM ticket。此前“独立PG保留内部库名”的建议已撤回，不再等待该选择。

不建立自动双向同步。后续重新克隆必须先保全验证结果和增量配置，再显式刷新；日常开发不等待迁移验收全部完成。KAF、Langfuse、PostgreSQL系统库及其它产品数据不在本次清理范围。

| 类别 | 处置 |
| --- | --- |

| 目录、分类、字段、SLA、流程定义与自定义配置 | 必须保留业务内容和可追溯来源；适配新模型的字段变化逐项记录，不能用seed整套覆盖 |
| 废弃测试业务数据 | 可整理或重建；实例7–10已确认废弃，其它先分类并列具名清单。终止活动流程使用领域路径，关联清理经验证后执行，保留必要操作证据 |
| 19条旧流程绑定 | 用途明确的逐项适配规范类型并验证路由，之后停用旧绑定；保留修改前配置及变更记录，不按字符串无差别替换 |
| 824与6条云业务绑定 | 保留定义和配置，停用并标记待适配；用途确认后再恢复，不凭名称推导目标类，不列为此次已恢复能力 |

保护配置不要求保留过时的启用状态，但不允许丢失自定义内容。若其依赖阻塞必要开发路径，应报告具体缺口，不伪造默认绑定或成功结果。

## 3. 四阶段执行与验收门槛

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1 固定范围 | 固定源码/制品、两个schema目标、数据与配置变更清单、备份恢复证据、运行profile、具名清理候选与消费者 | 目标身份明确，备份可恢复；身份/业务配置保留基线可核对；所有写入有明确范围 |
| 2 恢复Dev | 在副本验证最终变更包；维护窗口停止相关写入/消费者，升级原Dev、整理已识别测试数据、适配绑定，恢复3010→8080 | 结构及权限检查通过；身份与业务配置保全；readiness、登录、租户/权限及通用工单、变更、服务请求代表性UI路径通过。未适配能力明确列出 |
| 3 建立验证克隆 | 从验收Dev一致性快照恢复，保存来源、时间、摘要及附件边界；集成复用现有Toolkit，比较并应用获准迁移差异 | 克隆身份和关联完整，两个profile隔离；旧数据在新模型上的代表性UI路径可用；验证结束入口回Dev |
| 4 清理收尾 | 保全成果及证据后归档删除其余无用途ITSM业务/测试库、专属容器/卷与旧启动资源；同步当前入口 | 实际盘点只保留同库内Dev/验证两个长期ITSM数据目标；临时预演资源退出；备份作为文件保留；无遗留消费者或文档指向删除对象 |

结构迁移复用已预演的P037与普通032–036、039–047依赖链，不单独硬跑047，不修改历史SQL/校验和，不使用Ent补表，不执行独立R038退休。所需临时迁移权限限定操作窗口并验证撤销；应用身份不升级为owner。清理业务测试数据和旧环境不等于批准退休旧结构。

19条绑定调整、旧流程终止与最终配置验收要在最终副本验证中覆盖；已有结构预演证据继续复用，只对变化和未覆盖项补验。共享环境只有一个写入负责人，其他Agent可做独立只读审查。

## 4. 迁移成果与清理策略

既有五批384对象证据保留，不重新设计已采纳映射，也不冒充新克隆验收。按租户与稳定业务键比较新克隆：一致对象跳过，缺失/冲突列差异，再复用适用工具处理。Toolkit的users/departments能力不替代配置批次工具；旧收据不得复制成新库执行收据，示例/占位对象不自动补入。

`itsm_ga_ready`、`gb_replay_review`及历史对照库先保全成果，完成目标库差异核验后退出。删除清单必须具名列出实例、库、专属容器/卷、消费者、备份与恢复证明，逐项复核后按已确认范围执行；有活跃依赖的对象先迁移依赖，不能直接删。禁止按名称通配清库或删除共享PG容器/卷。异常发现范围外消费者时暂停该对象清理。

“仅保留Dev/验证两个schema数据目标”的验收覆盖维护中的WSL ITSM实例及历史ITSM专用实例；已停止容器中可恢复的旧数据库也须归档退出，不能仅停止后隐藏计数。备份文件不计为在线业务库，PG系统库不计入业务库数量。

## 5. 失败处理与恢复

- 执行前固定可恢复基线，包括数据库、角色配置及附件覆盖；任一关键保留检查失败，停止后续变更。
- 未开放开发写入时失败：在维护窗口按验证过的恢复步骤恢复原数据和匹配运行配置；禁止让当前代码继续连接不兼容结构。必要旧制品仅作为有明确退出条件的临时恢复，不作为长期开发方案。
- 开放开发后失败：优先前向修复；不得直接恢复旧备份覆盖新增业务数据。确需恢复时先保全新增数据并明确补偿方案。
- 克隆验证失败：保留证据，恢复Dev完整profile；不让验证故障长期占用开发入口。
- 新目标和恢复证据未通过前，不删除旧成果库和备份；历史库删除失败记录具体对象，不把阶段4标为完成。

## 6. 执行透明度与token预算

只维护一份执行清单，使用上述四阶段；每阶段汇报“完成、验证、阻塞、下一步”。默认简报，原始日志与敏感数据留私有证据目录。已有证据在源码、目标及条件未变化时复用；出现变更、失败或明确覆盖缺口才追加检查，不机械重跑全套。

串行处理共享写入，独立审查按必要风险边界安排，不启动重复调查。书面设计已确认，执行步骤维护在唯一清单；阶段门槛满足后开始相应环境操作；本文件提交不代表已执行升级、停用、克隆或删除。

## 7. 接续设计：执行 Agent 的裁定与门槛

状态：总体方向已确认，详细选择由设计负责人完成，见[完整实施合同](2026-09-16-dev-schema-execution-contract.md)。下文概览若与完整合同冲突，以其具体裁定为准；任务包只负责实施步骤，执行Agent不再承担补设计。独立审查不代表代码或共享环境已完成。

### 7.1 Dev流程：先防止产生坏回调，再恢复新流程

采用最小领域配置修复：新发布generic流程版本使用现有`fulfillment`且`assigneeSource=work_item_assignee`的无handler任务；分派、解决、关闭继续由现有WorkItem领域命令负责。不得将`ticket_task/assign`节点直接加上该绑定属性来伪装兼容，不覆盖原定义65或旧运行。审批任务不得改成普通履约任务。新版本节点、拒绝分支修复、领域门禁及绑定范围均由完整合同§2固定；流程完成与工单关闭分别验收。

同时修复通用安全缺口（RequiredFields仅检查键存在，不能代替类型/非空校验；用户输入错误与原定义缺陷blocked合同分别处理）：`ticket_service_handler`的assign要求assignee_id，update_status要求new_status；完成任务前按后端契约拒绝缺失输入，失败不能落地completed任务或待重试回调。当前简单任务UI不支持输入表单，因此后端必须对需要输入的任务撤销简单complete操作并解释原因；不借此实现任意动态表单平台。固定定义参数如何合入必须沿用现有权威解析顺序，禁止UI从旧instance变量拼接actor/tenant/assignee。

工单29/流程27/任务33/callback2保留失败证据。此次输入校验不能修复已冻结回调。禁止回填payload、重置任务或把handler_error改成成功。旧无效回调由完整合同§2.3确定采用现有blocked outcome停止重试，保留具名失败实例；不新增恢复接口、不强制终止、不宣称历史效果已证明。

### 7.2 schema克隆：来源回执与目标准入分离

Dev保留`public`；建议验证schema名`migration_validation`，实际创建前检查同名对象。克隆是一致快照下的完整新系统Dev数据副本，保留身份、配置、关联和真实历史；不等于旧ITSM历史ticket导入。单纯初始化空schema再导入少量配置不得报告为Dev克隆。

原P证据、原schema_migrations及其摘要按来源保留。新目标身份、角色与结构的适配必须形成独立、不可冒充历史迁移的克隆准入记录。记录至少包含：格式版本、来源database/schema/deployment、源制品/备份/账本/P证据摘要、快照截止点、目标database/schema/deployment、目标角色和授权摘要、结构映射摘要、操作者/时间、验收结果。不得使用源记录“证明”目标迁移曾重新执行。

克隆准入只由现有Migrator的显式离线操作生成，运行服务保持只读检查；不得增加启动自修复或宽松clone开关。方案使用规范迁移创建的专用表承载新记录，最终DDL及准入生命周期按完整合同§3实现和独立复核；业务身份不能读取/写入，独立inspection身份只能读取所需证据；可信control配置绑定目标及准入记录摘要。不得形成第二套迁移账本。若新增规范迁移，使用执行时下一可用编号，并同步环境结构目标；047是当前已部署基线，不是禁止后续迁移的永久上限。

解决引导顺序：先在来源以正常准入执行承载记录所需的新迁移，再快照复制至目标；目标最初禁止启动，显式克隆准入操作验证保留来源证据、目标结构/角色/数据后写入一次目标记录。普通运行/升级只能在完整克隆准入验证成功后继续。准入快照摘要与后续普通迁移后的当前结构证明必须区分，升级与撤销/刷新规则见完整合同§3，clone rollback/reset明确拒绝；不得永久比较旧全结构摘要或直接跳过漂移检测。克隆模式不能成为接受任意损坏目标的后门；目标R退休保持拒绝，另有设计前不得复用源P跨目标执行R。

仅允许明确的schema限定名和受审角色映射；索引、外键、序列默认值、函数体、触发器、RLS及SECURITY DEFINER必须验证无Dev业务对象引用。禁止对整份SQL做全局字符串替换。原始备份不变，转换产物单独记摘要。相同输入重试不得覆盖目标；新一次刷新使用停写、保全、显式删除重建及新证据，不静默覆盖已有验证结果。

权限隔离必须使用实际runtime/system/inspection角色验证显式跨schema访问拒绝，不能只依赖search_path。撤销PUBLIC/schema默认授权前列影响范围并核验现有依赖。每条连接只选择一个应用schema；缺少或错误schema直接拒绝，不回落public。inspection与business必须在同一实际实例/数据库/schema。新schema启动前默认关闭全部消费者，复制来的待处理任务/Outbox不自动执行；只对本次新验收记录开放经过审查的消费者范围。

已知工具缺口：`scripts/migration/target.py`目前固定search_path为public，Toolkit的apply仍因API/数据库目标绑定缺失而关闭。二者都必须修复和验证后才可真实回填。不得只把SQL读端指向验证schema、HTTP写端仍指向Dev。

### 7.3 交付边界

本轮只设计和提交文档；用户自行指派执行Agent。Agent A修复Dev，Agent B实现schema克隆，独立审查者分别验收，集成负责人独占共享环境写入。B的代码分析/离线实现可与A并行；真实Dev结构升级和克隆需唯一清单阶段2完整验收及B独立审查后串行执行；A的generic验收不能替代Change/Service Request及配置保全门槛。最终旧库清理依赖克隆与迁移验收，ITSM/KAF单PG合并仍复用既有任务三，不在本任务顺带搬迁KAF。
