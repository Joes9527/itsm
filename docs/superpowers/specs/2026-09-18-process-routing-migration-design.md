# 《流程与路由》设计：审批找人 + 派单迁移

- 日期：2026-09-18
- 状态：**proposed（待评审）**。设计意图，不代表已实现或已迁移；无数据库写入授权。
- 范围：审批人解析规则、兜底策略、旧派单路由迁移与可表达性结论、分类对齐；不包含 BPMN 流程本体迁移。
- 共同前提：[统一数据契约](./2026-09-18-org-people-data-contract-design.md)；数据依据：[对账与全景审计](../../review/2026-09-18-legacy-ehr-new-itsm-data-reconciliation.md)。

## 1. 业务目标

一张单子建出来后：**该谁审批就找到谁**（不落到通用组）、**该谁处理就进谁的队列**（旧派单习惯尽量不丢）。

## 2. 审批找人规则

五种方式全部提供，沿**两条轴**取数：

| 方式 | 取数轴 | 说明 |
| --- | --- | --- |
| 直属上级 | 人的轴 | 提单人的上级 |
| 沿链第 N 级 | 人的轴 | 上级的上级… |
| 所在组织负责人 | 组织的轴 | 从提单人所在组往上，取**第一个有负责人的节点** |
| 固定岗位 / 角色 | 不看提单人 | 如 IT 总监、网络运维 |
| 指定人或组 | 不看提单人 | 兼容旧习惯的兜底配置 |

规则：

- **级数由每种申请自己配**（系统不写死）。
- **兜底链**：该方式找不到 → 沿该方式的轴继续往上找（**跳过离职的人**）→ 到顶仍未命中 → **兜底审批组**。
- **自我审批**：解析结果若为申请人本人，视为未命中，继续往上 / 兜底。
- **留痕（必须）**：每次解析记录——用了哪种方式、命中谁、是否退级、退级原因。**兜底件必须可见、可统计**，禁止静默广播。
- 候选解析失败必须 fail-closed，不静默返回"成功但无人"。

### 2.1 解析器契约（实现规范）

现状：只有 `personal_manager_gm`（沿 `manager_id` 找总经理）与 `dept_manager`（沿部门父链找经理）。新增与扩展必须遵守：

1. **命名与语义**
   - `direct_manager`：直属上级解析器；接受 `level` 参数，`level=1` 为直属上级，`level=2` 为隔级上级，依次类推。五种找人方式在这里统一落地，不再新增语义重叠的 resolver。
2. **环路与自我保护**
   - 复用现有 `PersonalManagerResolver` 的 `visited map[int]bool` 环路阻断模式；
   - 解析结果为提单人本人时**强制视为未命中**，按兜底链继续，不得直接返回；
   - 现状说明：三个既有调用点已排除本人（`bpmn_process_engine.go:2124` / `:2159` / `:2286`），本契约要求新增 resolver 自带该保护，不依赖调用方。
3. **租户与在职**
   - 所有查询必须带 `tenant_id`；命中对象必须 `active`；跨租户一律 fail-closed（见契约 §3.1）。
4. **只读快照**
   - 解析输入来自流程实例的冻结快照（契约 §4.1），不得在节点解析时实时读 `users.manager_id` / `departments.manager_id`。

### 2.2 解析元数据持久化（可观测性）

任务创建时必须把解析链路写入任务扩展字段（不写敏感内容）：

```json
{"resolved_by": "direct_manager", "target_user_id": 123, "hop_count": 1,
 "fallback_applied": false, "skipped_inactive": []}
```

触发兜底时置 `is_fallback: true` 并记录退级原因。管理端据此统计**兜底率**并设上限告警；满足"禁止静默广播"。

## 3. 派单到处理组

- 目标：**分类 / 服务 → 处理组（队列）**优先；个别必须指人的再指定。
- 提单后自动派单；组内**谁先领谁处理**，避免锁定到某个人休假即卡死。
- 兜底组与处理组的区别必须在数据与界面中可区分，便于运营统计。

## 4. 旧派单路由可表达性（生产口径实测）

旧系统结构（生产 `keas-itsm.gazellio.com`，2026-09-18 只读抽取 1085 条）：

- 只落在 **4 个流程定义**：`orderRequest` 634、`sj002` 321、`knowledgeProcess` 128、`SJ001` 2。
- 只覆盖 **11 个旧环节**（`handleWith` 632、`sjcl002` 319、`KNOWLEDGE_*` 等）。
- 授权对象：具体人 907 条、角色 81 条、**已失效 97 条**；悬空分类涉及 **150 条**。

新系统当前能力（读代码实测）：

| 维度 | 现在支持 | 现在不支持 |
| --- | --- | --- |
| 条件字段 | 分类（精确 / 子树）、状态、优先级、部门、申请人、受理人 | **按业务系统 / 办公地点 / 基础设施做条件** |
| 动作 | 指定人、轮流、按负载 | **角色 / 组 / 队列动作** |
| 触发时机 | 建单时 | 流程中间节点（属 BPMN 节点职责） |

套算结果（节点归类为名称/路径启发式，需业务分流表确认；目标可用性按新库实测）：

| 结果 | 条数 | 占比 |
| --- | --- | --- |
| A. 条件可表达**且目标人在新库** | **6** | 0.6% |
| A′. 条件可表达，但**目标人属于"1261 人"缺口**（需先裁定人员） | **12** | 1.1% |
| B. 条件挂在"业务系统 / 地点 / 基础设施"上，目标可解析，需新增条件能力 | **821** | 75.7% |
| C. 已是失效引用（悬空分类 150 / 对象已删 96 / 排除节点 6） | **246** | 22.7% |
| 合计 | 1085 | 100% |

B 再拆：目标是**人** 757 条、目标是**角色** 64 条（角色还需展开成具体用户）。

**目标可用性的进一步事实**：

- 874 条的目标用户在新 ITSM 存在；**13 条的目标人正是"旧 ITIL 活跃但新库缺失"的 1261 人**（如 `handleWith`/`sjcl002` 的 `kehao.zhang`、`sjsubmit002` 的 `t_eng01`）；其余为角色或未解析。
- 其中 **12 条就落在 A′**——即"首期可迁的 18 条"里有 12 条因人员缺口而暂时无法落地，**真正可首期落地的是 6 条**。
- 那 97 条"已失效"（23 个 id）与 1261 人**零交集**，确认是旧系统里已删除的账号，作废判断成立。

**本质**：旧派单是"**你申请的这套系统 / 这个地点 / 这块基础设施归谁受理**"，而新引擎只会"按分类找人"，且分类树按设计不放业务系统与地点。这不是写映射能解决的。

### 4.1 分批策略（已确认方向）

1. **首期**：迁移 A 类 **6** 条。
2. **随人员裁定**：A′ 类 **12** 条与"1261 人在职裁定"绑定，裁定为在职后即可迁；**不预先补造账号**。
3. **作废**：C 类 **246** 条。
4. **产品需求**：把"按业务系统 / 地点 / 基础设施派单"和"角色 / 组 / 队列动作"列为后续能力。
5. **后续**：能力到位后再迁移 B 类 **821** 条。
6. 全过程**不做静默丢弃**：每一条记录去向（已迁 / 待能力 / 待人员裁定 / 作废）。

### 4.2 作废必须留审计清单

C 类 246 条**严禁物理丢弃**。迁移脚本或证据台账必须产出可归档的 JSON/SQL 清单，逐条记录：

- 源规则主键（`ctiauthorizedId`）、`ctiId`、`definitionId`、`taskDefKey`、`moduleId`；
- `authorizedType` / `authorizedId`；
- **作废原因**：分类已删除 / 授权对象已删除 / 命中排除节点；
- 判定依据（抽取 manifest 摘要 + 身份解析摘要 + 判定时间）。

清单是后续"为什么这条规则没了"的唯一凭据，也是旧系统下线前的复核材料。

> 方向变更记录：既有续办清单曾写"首期旧路由不迁，使用人工分派和新规范流程"。本设计基于 2026-09-18 实测（可表达性 18/1085，其中目标人可用 6 条）**将其修订为分批迁移**；变更原因、范围与风险以本节为准，并需同步更新续办清单。

## 5. 分类对齐（旧路由的前置依赖）

- **新分类为准**；旧 CTI 107 个逐条映射到新分类 183 个（IT 出映射表、**业务确认**）。
- 无对应物的在新分类里补建正式分类。
- 旧 CTI 混有"业务系统""办公地点""基础设施"等非分类语义：按既有 G1 方向分流（业务系统 → CMDB CI、地点 → 组织），**不进分类树**。
- 旧分类与新分类**名称交集为 0**，因此禁止按名称自动合并；必须逐条映射并留痕。

## 6. SSL-VPN 切片（提前验证）

用真实员工账号跑一遍，验收：

1. "主管初审" → 命中该员工**真实直属上级**（而非现有静态测试账号 `supervisor_test`）。
2. "网络运维复审" → 命中固定岗位 / 组。
3. "IT 总监终审" → 命中固定角色。
4. 全程无一步落到"通用兜底组"才算通过。

## 7. 验收标准

- 任意真实员工提单，审批链每一级都能落到具体的人 / 角色 / 组；**兜底率可统计且有上限告警**。
- 每一级审批可回答"为什么是他"（依据可追溯）。
- 旧派单：已迁 / 待能力 / 待人员裁定 / 作废 **四态齐全**，无静默丢弃；C 类 246 条有归档清单。
- SSL-VPN 切片 4/4 通过。

## 8. 与现状的差距

- 新系统派单规则 **0 条**；旧 1085 条完全未迁。
- 审批设计器已有四种找人方式，**缺"沿链第 N 级"**；且兜底组目前只是广播，无可见性与统计。
- 分类名称交集 0，映射表尚不存在。
- 旧环节名（`handleWith` / `sjcl002` 等）是旧系统内部标识，**不能照抄**，必须人工映射到新流程节点。
- 解析元数据目前无落点（任务上没有 `resolved_by` / `is_fallback` 等字段），无法统计兜底率。

## 9. 依赖与开放问题

- 依赖：《组织》《部门》《人员》三份设计的落地；《统一数据契约》第 7 节落地前提。
- **依赖（阻塞首期）**：A′ 类 12 条依赖"1261 人在职裁定"；裁定前首期实际只能落地 **6** 条。
- 开放：兜底审批组的具体组成与负责人。
- 开放：821 条待能力路由的产品排期与验收门槛。
- 开放：知识类流程（`knowledgeProcess` 128 条）不属于 WorkItem，其规则去向需单列（排除或映射到知识域）。
- 开放：旧节点归类（业务系统 / 地点 / 基础设施）的**业务分流表**由谁确认；本设计的 A/B/C 划分依赖它才能定稿。
