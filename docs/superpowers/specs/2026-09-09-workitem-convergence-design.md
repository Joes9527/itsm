## 3. 方案选择

仅修局部错误交付快，但不能消除多入口分歧；重建统一生命周期引擎扩大范围并破坏专业所有权。采用统一设计、分批重构，每批完成一个可独立验收的权威边界。

“分批”是交付顺序，不是允许一个概念长期由新旧两套实现共同管理。已有能力优先复用；抽取共享逻辑必须去除实际重复，不能为了转发旧调用引入新层。

## 4. 专业动作与完成条件

下表定义动作语义，不要求三个域使用相同状态枚举。沿用各域规范状态；确需新增状态时，在实施计划中明确新记录和后续动作的规则，不为统一显示而改名，也不批量改写历史状态。

| 动作 | 前置条件与权威写入 | 关联行为 |
| --- | --- | --- |
| Incident：确认／开始处理 | 域权限、合法状态；确认响应证据时记录首次响应时间，重复动作不重置 | 不推进 Problem／Change |
| Incident：解决 | 服务已恢复；记录恢复方式、结果、执行人及恢复时间；有效 workaround 可以恢复服务 | 不要求 Problem 已解决 |
| Incident：关闭 | 已解决；完成用户确认或满足显式配置的关闭策略 | 保留恢复时间和计时历史 |
| Incident：重开 | 有服务仍未恢复或再次受影响的依据；校验状态与权限 | 不自动重开全部关联记录 |
| Problem：开始调查 | ProblemService 验证当前状态；调查记录管理过程和证据 | 不改变 Incident 状态 |
| Problem：记录 RCA／方案 | 正文沿用 Problem 权威字段；方法、证据和评审属于调查元数据 | Known Error 保持独立知识记录 |
| Problem：解决 | 根因明确、永久方案已实施且验证通过；记录方案、验证结果、验证人和时间 | 通知 Incident 负责人，默认不批量关闭 |
| Problem：关闭／重开 | 关闭要求已解决；重开须有根因未消除或验证失败依据 | 不级联更改其他域 |
| Change：授权／排期／实施 | 按标准、正常、紧急类型策略验证审批、风险、窗口和实施前提 | 审批仍通过现有 BPMN |
| Change：结果／评审／关闭 | 记录成功、失败或回滚，完成类型要求的实施后评审；关闭不等于成功 | 发布结果，由关联域决定验证和状态 |

Problem 只有 workaround 时不得成功解决。不实施永久修复时保留未解决事实；取消／终止必须有独立原因与审计，不能伪装成 resolved。并非所有 Problem 都必须创建 Change，只有涉及受控变更的方案才需要；必需修复 Change 的成功结果仍不能替代根因效果验证。

调查完成仅代表调查活动完成，不能直接写 Problem resolved。Change 成功不等于 Problem 已解决；Change 失败或回滚不等于 Incident 必须重开，必须判断服务实际影响。

合法重开时启动新的 SLA 周期，当前周期已用时间和暂停累计归零，以服务端确认的重开时间为起点；原始 createdAt 不变。旧周期的响应、恢复、解决、关闭时间及达标结果保留为历史事实，当前周期的响应／解决完成投影清空，并原子保存新周期、截止时间及 WorkItem 版本。是否允许关闭后重开作为本稿的执行建议：通过显式授权动作支持纠正，不允许通用字段编辑直接恢复状态。

## 5. 唯一执行路径与事务

WorkItem 拥有公共身份与能力；IncidentService、ProblemService、ChangeService 决定专业动作。HTTP、调查模块、BPMN Handler、自动化和批量入口调用同一领域动作，移除直接写状态的旁路。共享服务不得以 switch recordClass 承担全部专业状态机。

一次动作必须：

1. 从可信上下文取得 actor、tenant、source、correlation，验证域动作权限、行范围和参与者权限。
2. 在事务内读取权威记录，验证预期版本、当前状态和专业前提。
3. 原子更新专业数据、WorkItem 状态／公共时间／version、必需审计和可靠事件。
4. 任一必需写入失败整体回滚；冲突返回明确冲突结果。
5. 通知与关联建议由事务外消费者处理，通过幂等键防止重放。

RCA、分派和普通编辑也遵守同一个 WorkItem 版本约束。客户端提交预期版本；后台和工作流使用读取时的版本，不能用事务内刚读取的版本掩盖陈旧请求。冲突重试必须重新读取并验证，不得覆盖新数据。

审计失败不能降级成日志警告后成功。复用既有审计与 Outbox，不建立平行事件体系。前端动作状态由后端专业校验投影，拒绝结果给出缺失前提；UI 不重复实现业务状态机或授权规则。

## 6. 关系与联动

WorkItemRelation 是执行记录关系的唯一权威来源。创建目标 WorkItem、专业扩展、关系、审计及可靠事件在同一事务完成。关联已有记录时校验双方租户、可见性、源记录关系操作权限及类型允许的专业组合。Known Error 不强塞进 WorkItemRelation。

- investigated_by：Incident 指向负责根因调查的 Problem。
- resolved_by_change：Incident／Problem 指向为其执行修复的 Change；关系本身不证明已修复。
- related_to：一般上下文关联，不推导因果或自动完成。

本次不回填或转换旧关联表中的历史关系，也不凭表名推断因果。切换后的关系只通过 WorkItemRelation 新路径读写，不合并旧关系查询。旧数据的离线保全和旧结构删除遵循第 10 节；新路径中的跨租户、悬空、重复或方向冲突必须拒绝。本次保持同租户同 Incident 最多一条未软删除 investigated_by 的既有部分唯一约束（ent/schema/work_item_relation.go）；“未软删除”指关系自身，不按目标 Problem 是否终态判断。结构变更必须验证目标数据库已安装该约束，不顺带修改基数。

默认联动为“结果事件、通知或待验证动作”。自动推进仅允许显式配置的既有 BPMN／策略调用目标域动作；每个目标仍验证证据、权限、版本和租户。批量结果分别呈现成功、冲突、拒绝、失败，可幂等重试。不因通知失败回滚业务，也不报告虚假的全部成功。

## 7. SLA 权威与专业语义

复用既有 SLA 服务与持久化模型。策略应用只在建单、合法重开或显式授权重算时发生；详情、监控、报表使用同一已应用定义、截止时间和计时事实，禁止查询时再次匹配不同规则。配置变化不静默追溯旧记录；重算审计保留旧值、新值、依据和 actor。

- 响应达标比较实际首次响应与权威截止时间。
- 恢复／解决达标比较专业完成时点与截止时间；完成后不能继续按当前时间制造超时。
- 未完成记录才按当前计时时点判断到期。
- 暂停由专业服务产生有原因、起止与策略依据的计时事件；关联 Problem 本身不暂停 Incident。
- 重开统一归零并开启新周期，不提供“继续旧周期”的并行策略。新周期从服务端重开时间开始，响应／解决目标均重新计时，暂停累计为零。沿用上一周期已应用的目标时长和日历版本，重新计算截止时间；更换 SLA 定义只能通过显式授权重算。原周期结果不被覆盖，展示和报表分别呈现周期结果，不能以新周期覆盖旧违约。
- 已绑定 SLA 却无法取得原策略或日历版本时，重开整体失败，返回可见配置错误，不默认按 createdAt 或当前规则重算。原本依明确策略无需 SLA 的记录仍不生成计时器。重复重开请求幂等，不重复归零或创建周期。
- 此规则适用于各专业域本身允许的重开动作；不新增 Change 绕过评估和授权直接恢复实施的入口。
- 取消、失败、回滚不是成功解决，统计区分终止与达标。

本批修正现有目标，不把 Incident 恢复目标冒充 Problem 根因目标。新增调查、授权窗口等目标后续独立设计。

## 8. BPMN 身份与回调

沿用原设计：businessId 为 WorkItem ID，businessType 为 recordClass，businessKey 由二者组成。ProcessTask 从实例继承身份；审批决策快照与实例一致。保留变量不能被表单、脚本或回调覆盖。Release 在独立设计完成前保留显式遗留值，不能误映射为 Change。

本次不转换历史流程实例、审批快照或保留变量，也不自动重建其执行记录。新绑定和新实例必须使用规范 WorkItem 身份；部署时更新受维护的流程配置，不引入旧身份双解释。切换前盘点仍在运行／暂停的旧契约实例与待执行回调，等待其按原流程结束；存在未结束依赖时阻断切换，不擅自取消、迁移或在新版本恢复执行。历史数据按第 10 节离线保全，不作为新引擎查询或执行的兼容来源。未知类型／动作明确阻断且可观测。

回调通过窄接口调用领域服务；业务结果与回调幂等事实由既有可靠事务机制保证。通知通过事务外可靠执行，不保留 Handler 直接写专业状态的旧实现。

| 批次 | 完整边界 | 必须删除 | 验收证据 |
| --- | --- | --- | --- |
| 1 | 三域动作、版本、时间、审计及调查数据治理 | 调查直接改状态、通用更新或回调绕过领域动作的路径 | 多入口契约、并发、回滚、调查 PostgreSQL 测试 |
| 2 | 跨域关系与结果联动 | 旧关系应用读写、合并查询、重复关联逻辑 | 新路径完整性校验、旧调用归零、权限和幂等测试 |
| 3 | SLA、BPMN 身份、编号与前端契约 | 查询时二次匹配、旧身份写入及双解释、专业 ID 冒充编号 | 周期归零、旧实例排空门禁、完整业务路径测试 |

每个被替换概念在对应批次交付时仅有一套有效读写。表结构删除核对全部消费者，在唯一读写切换与观察验收通过后完成，仍属于同批交付；离线备份不是运行兼容层。不能把旧路径删除留作无明确交付边界的后续事项。

## 10. 历史数据范围、结构切换与恢复

本次不迁移历史业务数据：不回填旧关系，不转换旧流程身份，不补造历史 Problem 验证证据，不重算历史 SLA，也不批量改变历史已解决／关闭状态。正式 schema 变更仍需版本化迁移脚本；“不迁移历史数据”不等于无需结构变更。

保留在现有权威表且符合新结构的记录不做批量改写；后续动作统一通过新领域规则。历史 Problem 缺少永久方案验证证据时不伪造或自动重开；若继续关闭或重开后再次解决，必须满足新的完成条件。未经新规则验证的旧结果不能被报表宣称为已验证永久修复。

旧结构内数据在删除前做可恢复离线备份，不接入运行时查询或建立历史兼容服务。本指令不授权无备份删除业务数据或取消未完成流程。若存在必须在线继续使用的旧数据或未结束流程依赖，切换门禁失败，先报告具体阻塞，不自动扩大迁移范围。

实施计划必须列明具体表、列、约束、调用方、备份内容、锁定范围与执行命令；本文不授权直接执行结构变更。

本次切换顺序明确为：隔离 PostgreSQL 演练 → 目标库只读盘点并排空旧流程依赖 → 验证可恢复备份 → 暂停相关写入及消费者 → 应用新结构并完成约束／记录完整性核对 → 切换唯一新读写 → 完整业务验收 → 恢复新路径写入并观察 → 再次核对备份、消费者和验收证据 → 删除旧结构 → 删除后健康检查。不可逆删除之前必须完成完整核对；这里核对的是保留数据完整性和新路径行为，不要求历史数据映射迁移。

观察期间旧结构禁止应用读写，新系统只有一套生效路径。观察窗口以实施计划列明的真实业务路径、计时和回调场景全部通过、无未解释错误且维护者／独立审查者确认作为退出条件；条件未满足不得删除或宣布该批交付完成。此顺序细化原设计的对账与观察后删除原则；本次历史数据免迁移范围明确替代原设计中要求历史关系／实例回填的条款，仅适用于本次优化。

跨租户记录、未处理消费者、在线旧契约依赖或保留数据计数差异必须阻断，不能猜测租户或语义。结构变更有版本记录且可重入，重复执行不创建重复业务记录。调查表纳入正式迁移、权限和 tenant/RLS 验证，不以启动建表或临时 SQL 代替交付。

删除旧结构且发生新写入后，不允许只回滚二进制。恢复必须协调数据库与应用版本，或采用评审后的前向修复；恢复备份时明确切换后数据的补偿范围。共享环境变更由单个协调任务执行。

## 11. 验收矩阵

| 场景 | 必须证明的结果 |
| --- | --- |
| Incident 经 workaround 恢复，Problem 未解决 | Incident 可解决且记录证据；Problem 状态不变；计时独立 |
| Problem 仅完成调查或只有 workaround | 后端拒绝 resolve，无半写入 |
| Change 成功但根因验证失败 | 保留 Change 真实结果，Problem 不解决 |
| Change 失败／回滚 | 不自动解决关联记录；重开需独立依据 |
| RCA／编辑／状态并发 | 陈旧版本冲突，不覆盖权威字段 |
| 审计或事件写入失败 | 整体回滚，无孤立扩展或关联 |
| 自动化重复执行，部分目标失败 | 不重复副作用；每条结果可见并可重试 |
| 跨租户、MSP 越界或缺域权限 | 后端失败关闭，不只依赖 UI |
| 修改 SLA 配置后查询旧记录；已按时完成后时间推进 | 页面、监控、报表一致，不追溯制造超时 |
| 暂停、恢复、工作日边界 | 相同计时依据，保留周期证据 |
| 按时解决 → 重开 → 再次解决 | 重开时当前响应／解决已用时间和暂停累计均为零；createdAt 不变；新截止时间以重开时点及原目标／日历版本计算，旧周期结果不变 |
| 旧周期已违约后重开，或重复重开请求 | 旧违约仍可追溯；新周期独立判断；重复请求不再次归零 |
| 已绑定 SLA 但策略／日历版本不可用 | 重开事务整体失败，不半改状态或猜测规则 |
| 历史数据免迁移 | 不产生旧关系／实例回填，不补造 Problem 验证证据，不更改历史 SLA 结果；保留历史记录的后续动作遵守新规则 |
| 旧流程未排空或存在在线旧数据依赖 | 阻断切换，不自动取消、丢弃或迁移 |
| 观察验收未通过 | 旧路径仍禁止读写，旧结构不删除；备份与恢复材料完整 |
| generic／Requested Item 回归 | 创建、权限、评论、附件、审批不退化 |

测试分层：领域单元测试，真实 PostgreSQL 事务／版本／RLS／迁移测试，前后端 API 契约，WMS 风格 Incident→Problem→Change→验证浏览器路径。SQLite 不足以证明 PostgreSQL SQL 与 RLS 正确。每批运行受影响检查和 git diff --check，由独立审查者／维护者复核。
