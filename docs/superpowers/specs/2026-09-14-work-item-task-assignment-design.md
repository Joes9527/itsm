## 1. 已确认的业务行为

通用受理型目录由 Helpdesk 受理，工单当前已分配处理人执行，申请人确认。执行任务生成后，工单从 A 改派给 B，尚未完成的绑定执行任务随之交给 B，保留改派审计。直接审批型目录保留原来的首节点，不增加统一受理步骤。

只对流程显式声明“绑定工单处理人”的人工执行节点生效。审批节点、申请人确认节点、固定人员任务、候选领取任务和外部委派保持各自职责。已经完成或取消的任务不重新分配；新配置只用于新实例，不修改历史流程定义或批量修复旧任务。

## 2. 核验背景

- `service/bpmn_types.go` 的 BPMNUserTask 只有字面量 assignee 和候选配置，没有可用的动态 assignee 来源契约；不能直接写 `${assignee_id}`。
- `service/bpmn_process_engine.go` 的 createUserTask 把参与人落到 ProcessTask。候选路由回退问题已修复，动态工单负责人解析尚未实现。
- `repository/ticket/repository_impl.go` 的 Update 使用工单 version 做条件写入，但不负责流程任务。
- `TicketService.AssignTicket`、TicketWorkflowService.ForwardTicket、批量/智能分配、生命周期升级及 BPMN 工单回调中存在负责人写入路径。这里只核验到相关源码入口，不能声称每条路径当前均在生产路由可达；实施前须形成可达写入清单。
- BPMN AssignTask/DelegateTask 已有任务权限、租户、生命周期、条件更新和审计，不能以普通工单改派调用其外部接口并伪造任务管理员身份。
- ProcessTask.task_variables 是参与者可写表单数据，schema 明确禁止存系统路由元数据。负责人来源不得放入该 JSON 字段。

## 3. 方案比较与选择

推荐实时绑定：WorkItem.assignee_id 是绑定执行任务的当前负责人来源，任务只存不可变的绑定方式。列表、详情、动作投影和命令授权使用同一个后端解析规则。改派不维护第二份可独立修改的人员值。

不采用“改工单后异步再改任务”：这会出现 A 在同步前继续执行的窗口，并需要重试及重复人员写入。不采用“只在任务创建时复制负责人”：它不能满足已确认的改派后同步生效行为。

固定人员、审批和候选任务继续采用现有任务分配方式。它们与绑定工单的执行任务是不同的配置语义，不是同一功能的新旧双实现。

## 4. 定义与存储契约

在既有 BPMN userTask 扩展加入 `assigneeSource="work_item_assignee"`，首批仅允许 `taskPurpose="fulfillment"` 的普通人工任务。仅支持该显式值；未知值、与 assignee/candidateUsers/candidateGroups 或审批分配属性同时使用、以及用于外部委派/审批节点均在发布校验阶段拒绝。运行时再次校验，不能因不认识配置而回退申请人。

ProcessTask 增加结构化、不可由任务表单接口修改的 `assignee_source` 字段。空值表示既有独立分配语义，`work_item_assignee` 表示绑定。由已固定版本的流程定义生成，不从启动请求、实例变量或前端声明接受该值。此字段是执行契约快照，不是另一份当前人员信息。

绑定任务的持久化 assignee 保持空值；候选字段也为空。后端响应中的 assignee 为有效负责人的投影，并附 assigneeSource 和 assignmentState（assigned / unassigned / unavailable / terminal），明确区分“缺少处理人”和“待领取”。

终态停止解析当前工单负责人：完成/取消事务的既有审计事件保存当时 responsibleUserId（可为空）和实际 actorId，两者分别表示终结时负责人和实际操作人，管理员取消时不得混为一人。这是不可变历史事实，不是第二份当前人员字段。终态响应 assignmentState=terminal，assignee 投影该终结审计中的负责人，操作人另行展示；缺失审计时显式 unavailable，不回退当前负责人。列表、统计和详情采用相同终态规则。普通用户读取终态任务仍需既有读取权限，参与者范围按终结时负责人判断；被提前改派的 A 不因过去曾负责而永久获得任务读取权。管理员全量读取只豁免参与者限制，仍须满足第 5 节的租户、WorkItem 可见性和专业权限；工单本身的读取权限不等于全部流程任务读取权限。

需要新增版本化 schema 迁移及生成代码，保持既有迁移文件字节不变。旧任务 assignee_source 为空，不做历史人员回填。本文不授权执行共享数据库迁移；实施阶段先完成可审查迁移、回滚/补救边界与环境前置检查。

## 5. 权威解析与访问控制

在既有 BPMN 服务边界内集中解析绑定参与人，通过实例权威 tenant/business identity 找到 WorkItem；不得信任可写变量中的 business_id、assignee_id 或 requester_id。只接受已验证的 WorkItem 业务身份，未知类型、缺失记录、租户不匹配均显式失败。

列表过滤、统计、分页总数、详情和 uiActions 都必须理解绑定来源，不能先按旧 assignee 筛掉任务再在前端补齐。绑定任务读取和操作的授权为以下条件的交集：目标租户/MSP 授权、关联 WorkItem 可见性及行级范围、对应 recordClass 的专业资源权限、BPMN 读取/命令权限、任务参与者资格。完成时还须重新验证 WorkItem 版本与专业动作权限。复用现有权威 WorkItem/专业授权服务，不在 BPMN 内复制专业规则，也不能仅沿用当前只检查租户和参与者的任务授权。

明确 elevated 权限只允许豁免参与者限制，不能跳过上述业务权限交集；CanReadAllTasks/CanUpdateAllTasks 不能作为整条授权链的直接成功返回。授权过滤必须在分页和计数前应用，防止不可见任务及其数量泄漏。绑定只确定“谁负责”，不授予 B 原本没有的业务或 BPMN 权限。

绑定任务不允许单独领取、分配或委派；其改派入口是已授权的工单分配。管理员读取/统计仍受既有权限控制，不能以绑定来源绕过原有租户/MSP边界。后端命令必须拒绝此类直接任务改派，不能只隐藏按钮。审批仍使用既有决策接口；不改变审批人授权。

没有有效处理人时，任务保留为未完成并显示等待分配/处理人不可用，不产生完成动作、不回退申请人。分配给目标租户内有效人员，或通过既有目录与当前代管分配策略授权的有效 MSP 人员后即可重新解析，不能依赖人工重建实例。申请人仅看到既有受控范围，不因此得到全部任务读取权限。

## 6. 改派、完成与审计

改派与执行命令以同一 WorkItem 行作为并发串行化边界：绑定任务完成时，在事务中先锁定 WorkItem，再读取并校验当前负责人，随后执行现有任务条件更新、回调和审计。任务生成也使用该边界，避免改派与生成交错。涉及实例变更时统一锁顺序为 WorkItem → ProcessInstance → ProcessTask；不需实例写锁的操作可跳过中间层，任务按 ID 稳定顺序处理，不得反向等待工单。所有受影响入口在实施前核对既有回调锁序。

终态证据覆盖直接取消、实例终止批量取消及其他实际可达的级联取消入口。现有 TerminateProcess 只写实例终止审计，不能作为任务级终态证据：必须在同一事务和上述 WorkItem 串行化边界内，为每个实际转为 cancelled 的绑定任务保存 responsibleUserId、actorId/source、tenant、taskId 和取消原因，同时保留实例级审计。已经终态的任务不覆盖其原有证据。任一任务状态或审计写入失败，整个终止事务回滚；改派与终止竞争时，终态负责人由锁定后的权威值决定。

工单从 A 改派 B 后返回成功，依赖负责人身份的普通参与者 A 随后开始的完成请求必须拒绝；并发时允许先取得锁的合法完成提交，改派不能追溯修改已完成任务。管理员代办保留参与者豁免，但仍通过第 5 节完整授权交集及生命周期校验。受控内部级联使用既有 service identity 和可信来源边界，验证目标租户与专业动作授权；不能伪造普通负责人身份或复用管理员提前放行，并记录实际 actor/source。绑定任务的领取/完成权限不使用跨请求缓存或创建快照。B 若无执行权限，改派不能被当作隐式授权；界面应明确显示任务不可执行的原因，不能显示可完成却返回权限错误的虚假动作。

在现有应用服务边界收敛可达的负责人写入：人工、转交所有权、批量、智能分配和流程回调都复用一个具备调用者事务能力的分配操作。专业领域仍拥有自己的状态校验；共享分配操作只处理共同的负责人、租户、版本和审计。移除被替代的直接负责人写入，不保留长期双路径；仓储或 Ent hook 不向上调用 BPMN 服务。

改派审计与负责人变更在同一事务中提交，记录 actor/source、tenant、WorkItem、旧/新人员、原因与当时受影响的未完成绑定任务标识。可复用既有 BPMN/工单审计存储，不新建审计引擎；历史事实可保存当时人员，但不是当前负责人字段的第二来源。审计写入失败则改派回滚。

改派通知复用既有 Outbox/Event：负责人变更、审计和通知事件在同一事务持久化，事件写入失败则整体回滚。事件携带 WorkItem ID、recordClass、变更版本、旧/新人员及 actor/source；MSP 操作分别保留 actorTenantId 和 targetTenantId。消费者提交后执行外部通知，以稳定事件标识幂等处理，复用既有重试与可观察失败机制。提交后进程退出不得丢失事件；通知发送失败不撤销已提交改派。替换受影响路径中的临时 goroutine/直接发送，不能在保留旧通知路径的同时再发 Outbox 通知，也不能把外部发送放进事务。

## 7. 实施拆分与验收门禁

1. 盘点全部可达负责人写入与绑定任务读取/命令入口，确认事务传递及锁顺序。不可达旧代码不趁机大规模清理，但不得遗漏可绕过审计的生产路径。
2. 定义、发布校验、结构化绑定字段及权威参与人解析；覆盖未知来源、冲突配置和越权变量注入。
3. 打通列表、分页、详情、uiActions 与命令授权交集。覆盖具备 BPMN 权限但缺少专业权限、缺少 WorkItem 可见范围、跨租户/MSP 未授权的用户，以及只有 elevated BPMN 权限的管理员：读取、计数和命令均不得越权；正例 B 具备完整权限。旧候选领取和审批路径必须回归通过。
4. 收敛分配、所有取消入口与审计、补并发锁；测试审计失败回滚、改派与完成/任务创建/实例终止竞争，以及多任务终止任一审计失败时整体回滚。核对直接取消和实例批量取消的负责人/操作人快照、终态读取与历史稳定。
5. 验证 Outbox：事件插入失败时改派回滚，提交后消费者启动前进程退出仍可恢复投递，重复投递不重复产生业务通知，发送失败可重试且可观察；确认旧直接通知路径已移除。
6. 独立审查、迁移预检与受控部署后，用纯人工临时实例和具备既有 BPMN 命令权限的普通处理人验证 A→B 改派：A 刷新后不能完成且直接调用被拒绝，B 可见且可完成；另验现有管理员代办边界及终态负责人/操作人分离；确认意见与审计持久化，再清理本次测试数据。
7. 全部门禁通过后才发布通用目录新版本。Helpdesk 候选组必须先核验有效成员；保留目录各自的审批要求。九项目录配置整改与 Helpdesk 解决/关闭 UI 仍按上游 P1 顺序验收。

自动化必须包括真实 Postgres 事务竞争测试；SQLite 单测不能替代并发证明。前端验证现有页面的数据和动作，不在 UI 复制分配规则。纯人工验证不调用 KAF、VPN 授权或采购交付。

## 8. 范围和风险

本设计涉及 BPMN 定义、任务 schema、读取和命令权限、共享分配与审计；因此按架构调整处理。实施若改变 AGENTS.md 的公共契约，须同步 CLAUDE.md；本稿只是拟议设计，不提前改写两者的已生效规范。

最大风险是遗漏负责人写入入口、列表预筛选漏任务，以及锁顺序与现有回调冲突。未通过这些检查前不得把 assignee_source 配置发布给生产目录。回退代码前必须先停止创建新绑定实例并逐项处理已有绑定实例，不能让旧二进制忽略新字段而退回申请人。

不包含历史实例修复、审批引擎替换、专业状态机重构、团队负载、知识库或智能建单集成。
