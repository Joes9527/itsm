## 4. 第一阶段设计

### 4.1 组件与数据所有权

- TicketDetail 负责路由身份、页面组合及父层计数同步，不承载附件和关系 CRUD 的第二套实现。
- 附件以现有 `components/business/detail-tabs/AttachmentPanel.tsx` 和 ticketAttachmentAdapter 为功能实现入口；在该组件内承接需要的工作台呈现。替换 TicketAttachmentGrid 的消费并检查其他消费者，无消费者后删除旧只读实现。
- 关系管理采用第 4.5 节统一 WorkItem 关系契约及依赖分支的组件/API client 作为唯一读写入口，不复活 RelationPanel/useTicketRelations 中没有后端实现的旧 CRUD。1A 仅修复当前只读关系的错误状态；1B 统一切换 TicketDetail 和 WorkItemShell 的关系消费者，核对后删除无消费者的旧实现。
- 不机械挂回整个旧界面。RelationPanel 中的占位父子/依赖视图不能被作为已完成功能重新暴露；1A 展示基线实际支持的父子关系，1B 仅提供统一领域契约允许的关系类型及方向，维持单一操作路径。
- TicketCommentStream 保留评论呈现与编辑器，继续消费 ticketCommentAdapter，补足错误、重试及请求身份处理。
- API 访问保留在 `src/lib/api/`，后端仍是权限、租户范围和关系合法性的权威来源。

### 4.2 附件与关联操作

- 附件空状态保留有权限用户的上传入口；上传展示进度，失败保留可重试状态；删除需确认；预览和下载走现有受保护接口。
- 恢复组件不等于证明底层 API 可用。实施时沿页面、adapter、API client、后端路由核对上传凭证、CSRF、文件限制和响应字段。若既有客户端契约阻止恢复操作，在原入口修复并补针对性测试。
- 1B 关联操作使用真实 source/target WorkItem ID、领域允许的关系类型及其 typed metadata；不保留旧 API 未获支持的自由说明字段。创建后刷新列表、计数和源版本；删除需确认，失败不得从列表永久移除。详情页当前 WorkItem 不一定是有向关系的源端，删除必须采用契约定义的正确方向和源授权。
- UI 门控遵循现有授权契约，不能从角色名称、persona、上传者身份或当前页面可见性自行推导授权。后端拒绝必须明确反馈。现有契约不足时记录并修复所属边界，不默认授权。
- 禁止自动扩大读取范围或跨租户关联；关系恢复不执行 Incident、Problem、Change 之间的生命周期转换。

### 4.3 错误、刷新与并发

- 首次读取失败：显示错误和重试，不能显示正常空状态；请求成功且结果为空时才显示暂无数据。
- 同一工单发生网络故障、超时或可恢复服务端错误时，保留已有列表并标注刷新失败。普通业务校验错误不自动归类为可恢复读取失败。服务端已确认变更成功但随后刷新失败时，分别提示保存结果与刷新结果，避免诱导重复提交。
- 已确认读取授权失效（权限拒绝、认证恢复失败或租户上下文失效）时，清除或遮蔽该面板内容、计数、缓存及未提交编辑状态，禁用操作；不能仅显示警告并保留敏感正文。安全客户端可完成的 CSRF 更新/认证刷新先遵循现有机制，不能把所有中间 403 都认定为权限撤销。会话或租户身份变化时同时使旧请求和缓存失效，迟到响应不得重新显示数据。
- 切换 ticketId：清除上一工单的数据、错误及未提交编辑状态；旧请求完成后不得覆盖新工单，也不得将上一工单草稿提交到下一工单。
- 写入进行中禁用重复提交；关闭弹窗不把未完成请求当作成功。
- 评论、附件、关联变更成功后，列表和父层 Tab 计数同步刷新。计数从对应查询结果派生，不增加第二份业务统计逻辑。
- 重试范围限制在失败面板；面板错误不能阻塞其他详情内容。

### 4.4 分配搜索

保留现有富文本选项呈现，为每个选项提供由姓名、用户名等现有展示字段组成的纯文本搜索值。过滤只对该字符串执行大小写归一化，移除用类型断言伪装字符串的做法。人员加载失败应可见且可重试，不能把权限拒绝显示为无人可分配；不扩展可分配人员的授权范围。

### 4.5 关系领域前置依赖与集成决策

复审结论纠正了“恢复旧 UI 即可恢复关系 CRUD”的假设。基线 router/router.go 只有关系列表和统计 GET；TicketDependencyService 仅将 tickets.parent_ticket_id 投影为 parent_child，ID 为 parent_child_<parent>_<child>。这些合成 ID 不能用于通用关系删除，旧前端枚举也不是支持类型的权威来源。

本设计选择复用统一关系领域交付，不在 UI 修复中补造旧 `/tickets/relations` 写接口或第二套关系存储。已核查的候选依赖提交为 `4660633019f10ec23835e23c7fa43578daa7ff57`，包含：

| 能力 | 候选依赖的已存在契约 |
| --- | --- |
| 源上下文 | GET `/api/v1/work-items/:id/relation-context`，返回 source 身份/版本与 mutation.allowed/reason；这是源端资格，不替代目标端和提交时校验 |
| 统一读取 | GET `/api/v1/work-items/:id/relations`，使用结构化关系身份及双方 WorkItem 信息 |
| 创建/删除 | POST / DELETE `/api/v1/work-items/:id/relations`，提交 sourceWorkItemId、targetWorkItemId、relationType、expectedVersion、稳定 operationId 及类型允许的 metadata；URL ID 必须等于 sourceWorkItemId |
| 回执 | 返回版本和 replayed 等操作回执，写入成功后另行刷新；结果不确定的重试保留同一逻辑操作身份，不以新 operationId 盲目再提交 |
| 前端入口 | `src/lib/api/workitem-relations.ts` 中的 WorkItemRelationsApi；具体支持类型与组合以领域契约为准，不从旧 ticket-relations 枚举映射猜测 |

该核查仅证明候选代码存在，不代表领域分支已审查通过、已集成或已部署。1B 的准入条件必须全部满足：

1. 关系领域交付及其必要前置项经独立审查并集成到主线；发布记录明确所需结构变更、历史父子关系的处置、唯一数据源切换及回滚边界。
2. UI 后续分支以集成后的主线为基线，记录实际 SHA 和对照后的 API/DTO。禁止只摘取控制器或客户端而遗漏授权、领域注册、事务、版本、审计和持久化依赖。
3. 目标测试环境的后端版本与所需迁移已核验；用隔离测试数据确认 source/target 的租户和行权限、允许类型、版本冲突、操作重放、审计以及创建/删除后重新读取。
4. 原 parent_ticket_id 投影与统一结构化关系的取代/保留规则由领域交付明确。UI 不双读合并、不自动转换合成 ID、不自行回填历史关系；如该规则未获确认，1B 不准入。

合并与发布顺序为：1A 可独立交付 → 关系领域及必要迁移交付 → 1B 接入并做契约/真实路径验收。依赖未满足时，1A 保留明确的只读关系能力，R3 保持未完成；不得恢复调用不存在接口的按钮。待依赖满足的关系功能是已登记的后续交付，不是失败请求时的静默降级。

## 6. 验收标准

| 范围 | 必须证明的结果 |
| --- | --- |
| 附件 | 空列表可上传；受允许文件上传成功后重新读取可见；删除取消不发请求、确认后重新读取不可见；预览/下载可用；超限和失败反馈明确 |
| 关联 | 1A 真实父子关系读取正确且无虚假写入口；1B 验证统一 context/list/add/remove、双方 WorkItem 身份、允许类型和方向、源版本冲突、同 operationId 重放、拒绝结果和持久化重新读取；领域未支持类型不可提交 |
| 搜索 | 输入姓名/用户名不会抛出 TypeError；正确匹配；空输入恢复列表；人员读取失败可重试 |
| 读取状态 | 评论/附件/关联分别覆盖首次失败、重试成功、正常空列表、可恢复刷新失败保留旧数据；成功读取后授权撤销必须清理内容、缓存、计数和编辑状态并禁用操作；切换工单/身份后旧响应不得恢复旧内容 |
| 刷新与计数 | 写入成功后列表和 Tab 计数一致；刷新失败明确提示；重复点击不重复提交 |
