# 《组织》设计：集团—多公司组织树

- 日期：2026-09-18
- 状态：**proposed（待评审）**。设计意图，不代表已实现或已迁移；无数据库写入授权。
- 范围：组织树的结构、节点类型、负责人、维护与校验；部门语义见《部门》设计，人员见《人员与汇报线》设计。
- 共同前提：[统一数据契约](./2026-09-18-org-people-data-contract-design.md)。
- 依据：[数据对账与全景审计](../../review/2026-09-18-legacy-ehr-new-itsm-data-reconciliation.md)。

## 1. 业务目标

组织树真实可用：集团 → 公司 → 分公司 → 部门 → 组可完整展开；每个节点的类型、负责人、员工数准确；迁移后由新 ITSM 长期维护。

## 2. 一棵树、四种节点

- 保留"组织节点"这一棵树（现有 `departments` 概念）；每个节点带一个**节点类型**：公司 / 分公司 / 部门 / 组。
- **允许少层**，子树深度不设上限。实测旧 ITIL 最深 14 层、eHR 最深 11 层，"公司下面直接是部门"是常态而非例外（旧 ITIL 94 个公司节点里 58 个、eHR 79 个里 67 个都如此），因此**不能用"处在第几层"判断类型**。
- **节点类型新增独立字段**，不复用现有 `org_type`。现有 `org_type`（`department` / `warehouse`）表达"是否仓库/物流节点"，是另一个维度，予以保留，与节点类型并存。
- 节点**编码唯一且不可修改**；名称可改并留痕；同名不同编码不得合并。

## 3. 树骨架与对齐

实测：旧 ITIL 生产组织导出 5202 节点（单根「组织架构」）；新 ITSM 现有 7975 节点（1 个真根 + 10 个孤儿 + 14 个产品种子），编码交集 4899，新库独有 3076，旧库独有 303。

建议做法：

1. **以旧 ITIL 的组织树为骨架**：它是员工真实归属与上级的来源，也是"一次性搬迁"的交付对象。
2. eHR 的编码做**对齐参照**，不单独作为权威。
3. 编码相同 → 视为同一节点；旧有 eHR 无 → 保留；eHR 有旧无 → 参照补建或忽略，逐条登记。
4. **把 7871 名员工重新落位到旧 ITIL 的最细节点**（按编码映射），替换当前 eHR 粗粒度归属（现为 175 个 9 位分公司级节点）。
5. 旧 ITIL 侧为单根，无孤儿问题；10 个 eHR 孤儿节点仅在补建参照时处理。
6. 14 个产品种子部门**隔离/打标**，不参与业务树；标记必须进入版本化迁移，不能只存在于某个数据库。

## 4. 维护与留痕

- 维护者：ITSM 管理员（迁移后旧系统下线，由新系统承担）。
- 可改：新增节点、改名、换父、换负责人、**停用**。
- 每次变更留痕：谁、何时、改了什么、为什么。
- 撤销 = 停用，不物理删除；有下级或在职员工的节点不能删除。

## 5. 查询与展示

- 组织树按节点类型可筛；默认从"集团"根展开。
- 节点上可见：负责人、员工数（按子树统计）、类型。
- 停用节点：历史可见，新单不可选。
- **性能契约（大树）**：节点量级近 8000，禁止一次性下发完整实体树。必须二选一或并用：
  - **轻量投影**：树接口只返回 `id / code / name / parent_id / node_type / manager_id(可选) / 是否有子节点`，不含大字段；
  - **按需懒加载**：以 `parent_id` 展开子节点，逐层加载。
- **子树统计**：员工数按子树统计**不得**在列表接口逐行递归实时计算；仅在节点详情或显式展开时按需/异步计算并缓存。

## 6. 硬性校验（fail-closed）

1. 不能成环；不能把节点挂到自己或自己的后代下。
2. 负责人必须是在职用户，且同节点唯一。
3. 有下级或在职员工的节点只能停用，不能删除。
4. 编码同租户内唯一、不可变；未知节点类型必须拒绝，不静默归类。
5. **数据库层约束**：`code` 当前无联合唯一索引，落地时必须建立 `UNIQUE (tenant_id, code)`（例如 `idx_departments_tenant_code`），否则导入重跑会产生脏重复，且"编码唯一"只是口头的。

## 7. 验收标准

- 迁移后组织树可完整打开，任一员工都能在树上定位。
- 按"先补公司/分公司"的要求，**每个公司/分公司都有负责人**。
- 组织改名后：历史单显示旧名，新单显示新名。
- 换负责人后：在途单审批人不变，新单用新人。
- 树中不存在环、不存在指向自己的父节点。

## 8. 与现状的差距

**实施计划的第 0 优先级前置项（阻塞后续一切导入）**：

1. `sync_ehr_master_data` 建部门**不幂等**（重跑会重复插入），必须先改为按 `(tenant_id, code)` upsert 或先建唯一索引，否则任何"重跑回填"都会污染组织树。
2. `departments.code` 缺 `UNIQUE (tenant_id, code)` 索引。

其余差距：

- `departments` 没有"节点类型"字段（现有 `org_type` 语义不同），需新增。
- 现有树接口 `department_service.go` 一次性 `All()` 加载全部节点、无分页；14 种子 / 10 孤儿未隔离。
- 现有组织负责人只有 1 条，且是手工留下的脏值（需按《部门》设计的原子前置步骤清除）。
- 员工归属粒度是分公司级，需改为最细的组。

## 9. 依赖与开放问题

- 依赖：《统一数据契约》第 7 节的落地前提（目标克隆库、生产源口径、seed 清理）。
- 开放：**"集团"是否也作为一个可挂负责人的节点**，还是仅作展示根。
- 开放：节点类型字典是否需要"虚拟组织 / 项目组"（当前未纳入首期）。
- 开放：员工数统计是否需要包含停用员工，或只算在职。
