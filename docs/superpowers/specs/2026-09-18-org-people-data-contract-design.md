## 1. 目的

审批不断流的根因不是缺一个函数，而是**四个词没有统一口径**："组织""部门""负责人""上级"。本契约先把它们钉死，四份设计再各自展开。

## 2. 六个定义

| 业务词 | 含义 | 谁维护 | 关键规则 |
| --- | --- | --- | --- |
| **组织节点** | 集团组织树上的一个位置 | ITSM（从旧 ITIL 一次性搬入后） | 具备：名称、编码、父节点、节点类型、负责人 |
| **公司 / 分公司 / 部门 / 组** | 组织节点的四种类型 | 同上 | 允许少层；**类型写在节点上，不靠第几层判断**；同名不同编码不合并 |
| **组织负责人** | 某个组织节点的正职负责人 | ITSM 管理员 | **一个节点最多一人**；必须是在职用户；副职与其他经理不算 |
| **直属上级** | 一个员工的直接汇报对象 | 从旧 ITIL 搬入，之后 ITSM 管理员 | **一人一上级**；必须同租户、在职、不能是自己；整条链不成环 |
| **员工归属** | 员工挂在组织树的哪个位置 | 同上 | **挂到最细的组**；换归属即换组织 |
| **组织快照** | 单据创建时记下的组织与上级 | 系统自动 | 历史单据不随后续变动改变；在途审批不换人 |

## 3. 两条互相独立的关系（最关键）

```
组织负责人  →  挂在「组织节点」上的属性（一个节点一个负责人）
直属上级    →  挂在「人」上的属性（一个人一个上级）
```

两者**不互相推导**：

- 某部门的负责人，不等于该部门每个人的直属上级；
- 某人的直属上级，不等于他所在部门的负责人。

混淆这两条会让审批时对时错，因此它们必须是两条独立数据，不设自动同步。

### 3.1 租户边界（公理，不可省）

**组织树父子关联、人员归属、直属上级、组织负责人、审批人解析、兜底组派发，全部必须限定在当前 WorkItem 的 `tenant_id` 范围内。** 任何跨租户的 `parent_id`、`manager_id`、负责人、候选人或兜底组都必须 **Fail-Closed 抛错**，不得静默降级为"找不到就广播"。

现状说明：三个审批解析调用点都已带 `TenantIDEQ`，数据库亦有 RLS 策略；本条是把既有事实提升为**实现契约**，防止后续新增解析器或新的树遍历遗漏该过滤。

## 4. 两条取数轴

- **人的轴**：直属上级 → 上级的上级 → …（用于"直属上级""沿链第 N 级"）
- **组织的轴**：员工所在组 → 上级部门 → 分公司 → 公司 → 集团（用于"所在组织负责人"，取这条轴上**第一个填了负责人的节点**）

两条轴各自往上找，互不替代；找不到时先沿本轴继续上行，到顶仍未命中才进入兜底组。

### 4.1 快照与解析留痕的落点（防止"在途换人"）

现状：`requester_id` 已在建单时冻结进流程实例变量（`bpmn_submitted_workitem_start.go` 有冻结校验），但**部门与上级是节点解析时实时读取 User 表的**；因此若第二级审批在第一级之后才创建，而期间上级被改动，第二级会换人。

实现契约：

1. **实例启动时冻结解析输入**：除现有 `requester_id` 外，把提单人的**组织路径快照**（所在节点 id + 编码路径）与**上级链快照**（有序 user id 列表，含环路检测与长度上限）写入流程实例变量。长度上限与截断行为必须显式声明，截断时按"到顶未命中"进入兜底，不得静默截短。
2. **节点只读快照**：审批节点的解析一律读取上述流程变量，**不再实时读 User / Department 主表**；"沿链第 N 级"从上级链快照取第 N 位。
3. **每个任务持久化解析结果**：任务创建时写入 `resolved_by`（解析方式）、`target_user_id`、`hop_count`、`is_fallback`、被跳过的离职人；已创建任务**永不重新解析**。
4. 由此满足 D12"在途审批不换人"，并让"为什么是他"可审计。

## 5. 变更规则

- 组织改名 / 换父 / 合并 / 拆分：**节点历史保留**；历史单据留快照；新单用新组织。
- 撤销：用**停用**，不物理删除。
- 负责人 / 上级变更：**只影响新单**；在途审批不换人。
- 负责人或上级离职：该节点 / 该人视为空缺，按第 4 节的轴往上，最终兜底。

## 6. 边界（本契约不覆盖）

- 新员工入职、员工离职的采集管道：由 **KAF** 负责；本契约只规定"人进入 ITSM 之后怎么放"。
- **长期治理依赖（必须在旧 ITIL 下线前解决）**：KAF 的 EHR 同步（`md_ehr_person`，来源 SOAP `getUserInfo`）当前**不含上级字段**，`ehr-data.xlsx` 的 `direct_supervisor` 也没有可复核的生成口径。旧 ITIL 一旦下线，**新入职员工将没有汇报线上游输入**。处置要求：要么扩展 KAF 管道支持上级字段，要么由 ITSM 提供管理后台的手工维护 / 批量导入能力，二者至少其一先落地。
- 分类树、派单规则本身：属《流程与路由》设计。
- 历史工单 / 审批 / 评论 / 附件 / 流程实例：**明确不迁移**。

## 9. 开放问题

- 兜底审批组的具体组成与负责人。
- 派单目标以"组/队列"为主还是允许直接指人。
- 部门"职责范围"是否进入首期。
- `047` / `048` 结构目标与实际 Dev 的漂移如何对齐（属环境合同更新，需单独确认）。
- §4.1 的上级链快照**长度上限**取值，以及截断时是"到顶兜底"还是"拒绝建单"。
- 上级链是**在实例启动时整体冻结**（严格"在途不换人"），还是**每个节点进入时取当时链路并冻结该节点**（已创建任务不换，但后续节点可感知变更）。当前设计按前者；若要放宽需显式记录。
