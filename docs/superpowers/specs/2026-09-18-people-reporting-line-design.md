# 《人员与汇报线》设计

- 日期：2026-09-18
- 状态：**proposed（待评审）**。设计意图，不代表已实现或已迁移；无数据库写入授权。
- 范围：员工记录、组织归属、直属上级、在职状态的使用与空缺处理；人员增减采集不在范围内。
- 共同前提：[统一数据契约](./2026-09-18-org-people-data-contract-design.md)。
- 依据：[数据对账与全景审计](../../review/2026-09-18-legacy-ehr-new-itsm-data-reconciliation.md)。

## 1. 业务目标

每个在职员工都能回答三个问题：**我在哪个组？我的直属上级是谁？如果上级空缺，系统会怎么办？**

## 2. 范围

- **管**：员工的组织归属、直属上级、在职状态的使用、为空 / 离职时的处理。
- **不管**：新员工入职、员工离职的采集——**由 KAF 负责**。本设计只处理"人进入 ITSM 之后"的事。

## 3. 员工关键信息

| 信息 | 含义 | 谁提供 / 谁维护 |
| --- | --- | --- |
| 工号（登录名） | 唯一身份 | KAF |
| 姓名 | 显示 | KAF |
| 在职状态 | 是否在职 | KAF |
| **归属** | 挂在组织树哪个节点 | 迁移自旧 ITIL，之后 ITSM 维护 |
| **直属上级** | 直接汇报对象 | 迁移自旧 ITIL，之后 ITSM 维护 |
| 岗位头衔 | 显示 / 辅助判断 | KAF |

## 4. 归属规则

- 挂到**最细的组**（旧 ITIL 原本就是按小组登记的，平均编码 18.3 字符；当前新库只到分公司级，平均 9.0 字符）。
- 归属为空：**不阻塞提单**，但审批走兜底。
- 换归属：历史单据保留快照，不追改。

## 5. 上级规则

- **一人一个上级**；必须是同租户**在职**用户；**不能是自己**；整条链**不能成环**。
- **上级离职** = 该人上级空缺 → 审批沿人的轴往上找（跳过离职的人），找不到才兜底。
- **到顶没有上级** → 兜底组。
- 上级不允许是外部 / 供应商账号（首期只认内部在职用户）。

## 6. 一次性迁移规则（从旧 ITIL 生产）

实测重叠用户 7753 中：新库上级有值 7042、旧 ITIL 有值 7683、可解析 7649；双方一致 6631、**冲突 404**、**仅旧有新无 614**、仅新有 7、都无 97；另有 **31 条"自己当自己上级"**。

迁移口径：

1. 以**旧 ITIL 的上级**为准写入；能解析到人的写入。
2. **解析失败、指向自己、会成环的一律留空并登记清单**——不猜、不补造。
3. 旧 ITIL 与 eHR 冲突的 404 条：**以旧 ITIL 为准**；eHR 仅作参考，不参与覆盖。
4. "仅旧有新无"的 614 条按第 1 条补入。
5. 31 条自引用清理为空。
6. 迁移后由 ITSM 维护；旧系统下线。

## 7. 与现状的差距

- 现在上级来自 eHR `direct_supervisor`，**要换成旧 ITIL**（614 补、404 覆盖）。
- **长期治理风险（P0，必须在旧 ITIL 下线前处置）**：KAF 的 EHR 同步（`md_ehr_person`，来源 SOAP `getUserInfo`）**没有上级字段**，`ehr-data.xlsx` 的 `direct_supervisor` 也找不到可复核的生成口径。旧 ITIL 是本设计唯一的上游汇报线来源，它一旦下线，**后续新入职员工将没有任何汇报线输入**。
  - 处置要求（二选一或并用）：**扩展 KAF EHR 管道以抓取上级字段**；或在 ITSM 提供管理后台的**手工维护 / 批量导入上级**能力。
  - 在任一路径落地前，不得把旧系统下线，或必须接受"新员工上级需人工补录"的运营成本。
- 现有 **31 条自引用**需清理。
- **防御性约束**：清理后必须在数据库或 Ent 层增加非自引用校验（如 `CHECK (manager_id <> id)` 或写入 Hook 拦截），防止后续再次写入脏数据。
  - 说明（与审查意见的差异）：BPMN 引擎的三个解析调用点**已经**排除申请人本人（`bpmn_process_engine.go:2124` / `:2159` / `:2286`），当前**不存在可直接利用的自审批漏洞**；该约束的目的是防止解析器被其他调用方复用时失去保护，以及消除脏数据导致的歧义。
- 员工归属需从分公司级改到最细的组。
- 旧 ITIL 活跃但新库缺失 1261 人（其中 1252 人在 eHR 中完全不存在）——**需 HR 裁定**是否为"已离职未停用"或"导出不全"；**不默认补录**，且不影响在职员工的归属与上级迁移。**该缺口已影响派单迁移**：13 条旧路由的目标人是这 1261 人中的成员，其中 12 条属于"首期可表达"的 18 条（详见《流程与路由》第 4 节）。

## 8. 验收标准

- 每个在职员工都能在组织树上定位，并能看到自己的上级（或明确显示为空）。
- 上级链能一路爬到顶，全程不成环；不存在自引用。
- 上级离职后，新单审批**不会指派给他**，而是自动往上或走兜底。
- 迁移产生的空值有清单、可解释，不含猜测值。

## 9. 依赖与开放问题

- 依赖：《组织》的节点与树对齐；《统一数据契约》第 7 节落地前提。
- 开放：离职人员名下**在途审批任务**的自动转出规则（建议转其上级或兜底组并留痕）需与《流程与路由》一起定。
- 开放：1261 人的在职状态裁定归属（HR / 业务）。

## 10. KAF 上游必须补充"直属上级"字段（硬前置条件，非本设计可解）

实测 KAF EHR 的人员表（`md_ehr_person`）**没有上级字段**，因此新 ITSM 无法从上游获得汇报线。
本设计已确定的自身能力（写入校验、导入时跳过并计数）**不能替代上游数据**：

- **影响**：上级为空期间，审批沿**组织的轴**向上找，最终落到兜底组（契约 §4），**不阻塞提单**。
- **前置动作**：向 HR / KAF 提出字段补充需求；在此之前，汇报线由 ITSM 侧的维护承担。
- **已决定的边界**：入职/离职采集由 KAF 处理，本设计不实现。

> **状态**：未完成的前置条件。不要把它当作"已解决"。

## 11. 实测数据口径（2026-09-18 只读盘点）

详见 `docs/migrations/2026-09-18-reporting-line-inventory.md`。两条会影响实现的口径：

- **"未设置上级"在库里是 `NULL` 而不是 `0`**：796 条。按 `manager_id = 0` 或 `<> 0` 过滤的 SQL 会静默漏掉它们（NULL 与任何值比较都不成立），判断时必须用 `coalesce(manager_id,0)`。
- **`users` 表没有 `deleted_at`**（只有 `departments` 有）；用户生命周期用 `active`。
- 实测分布：总数 7872、未设置上级 796、自引用 31、有效汇报线 7045、悬挂引用 0、上级已离职 0。
