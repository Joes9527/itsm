## 1. 文档定位

本次讨论覆盖 Incident、Problem、Change 和共享 WorkItem 能力，并将 generic、Requested Item 纳入公共能力回归。目标是完成已开始的 WorkItem 重构，不是只修 Incident，也不只是关闭 B/C1 报告中的几个缺陷。

本文件作为本轮后续开发输入的总入口，链接现有权威设计与局部决定，不创建第二份领域规范。依据仍为 AGENTS.md、[原 WorkItem 模型](2026-08-26-unified-work-item-model-design.md)和[accepted 收敛设计](2026-09-09-workitem-convergence-design.md)。本文件中的待讨论问题不能被实现者当作已批准需求。

[Incident 分配与处理动作设计](2026-09-11-workitem-incident-assignment-convergence-design.md)是已经讨论确认的一项子决策，不能替代总体开发输入，也不能直接套用于 Change 或 Problem。此前过早将讨论聚焦到 Incident 独立实施的安排由本文件纠正；继续讨论总体范围与各域差异后再形成相应实施计划。

## 3. 按专业域组织开发输入

| 范围 | 已有实现／已有契约 | 后续需要完成与核查 | 尚需讨论的边界 |
|---|---|---|---|
| Incident | WorkItem 基础身份、新生命周期命令、SLA 重开；旧 HTTP 分配与新 BPMN 分配并存 | 按已确认语义合并分配入口；调用方版本、幂等、审计/活动原子性和多入口一致性；保持恢复独立于 Problem | 本域已确认分配／开始的主要语义；其他入口差异须由盘点发现并记录，不能假定全部已收敛 |
| Problem | 独立调查、RCA、永久方案验证；resolve 检查必需 Change 的成功结果 | 核查分派、调查、方案修改、验证、解决、关闭和重开各入口；保证调查完成或 Change 成功不自动解决 Problem；单纯转派保留阶段、分析、方案与验证证据，并记录责任变更 | 主要转派语义已确认；转派原因必填；不新增交接审批。方案变化后的证据有效性沿用专业规则，盘点发现缺口时再明确 |
| Change | 独立 submit/assess/authorize/schedule/implement/outcome/review/close；BPMN 审批事实；metadata/assign 和生命周期动作分开 | 核查负责人调整、任务执行人、审批人及流程任务的真实关系；统一 HTTP/BPMN/自动化；保留评估、授权、实施窗口和 PIR 前提；仅协调负责人转派保留阶段与审批结果 | 实施任务执行人更换与获批方案的关系、当前任务如何移交仍需确认；不将协调负责人决定直接扩展为执行人规则 |
| Requested Item | 目录驱动创建、审批和履约，公共身份已委托基础记录 | 回归请求人/代申请、分派、审批、履约、评论附件及流程身份；不能套用 Incident 的 assigned 状态推进 | 仅当本轮共享变更暴露具体差异再讨论，不擅自增加目录订单或 Catalog Task 能力 |
| generic | 基础 WorkItem 和公共协作入口 | 回归创建、字段更新、分派、评论、附件、权限及流程绑定，确保专业收敛不破坏通用路径 | 不赋予 Incident/Problem/Change 专业状态语义 |

Change 当前代码提供不同于 Incident 的事实：`handlers/change/commands.go` 执行专业流程动作，`metadata.go` 单独处理负责人等元数据并校验未决回调，`action_availability.go` 根据权限、状态和当前流程任务投影可用动作。应沿用这些真实边界调查差异；不能因为名字都叫 assign 就统一套用 Incident 的状态转换，也不能仅凭已有分层认定所有入口都已正确。

### 页面与专业动作边界（既有设计核对）

2026-09-11：维护者询问“公共操作一致、专业动作各自保留”是否与 WorkItem 设计冲突。核对原设计第 5.1、12.2、17.3 节后，确认这是既有设计要求，不是需要重新批准的新页面架构：保留专业 URL，复用统一 WorkItem Shell 承载公共详情与协作能力，专业 Panel 承载专业内容；可用动作由后端计算。不能各域复制一套公共实现，也不能用统一按钮绕过专业服务。

负责人、状态等公共字段仍只写 WorkItem；是否允许转派以及转派对专业状态的影响，由对应专业规则校验。Incident 首次分配的状态推进与 Change/Problem 保留进度并不构成重复公共模型。本轮新确认的是转派业务细节，后续应对照既有页面契约核查 C2 实现缺口，不重复讨论已批准的架构方向。

### C2 公共详情实现核查（2026-09-11，静态证据）

在评审工作树核查 `WorkItemShell.tsx`、`WorkItemTypes.ts`、`WorkItemComments.tsx`、`WorkItemAttachments.tsx` 及原 runtime 子计划：

- 三个专业详情页已引用公共 Shell；Shell 的评论、附件、历史和关系区块均传入 `workItem.id`，评论与附件复用 ticket adapter。保留这部分实现，不重新创建平行公共详情。此处仅确认调用结构，不代表真实权限和持久化旅程已通过。
- `WorkItemCommon` 尚无 version；C2 已要求专业详情返回权威编号、WorkItem ID 和版本，动作携带观察版本与操作键。需打通实际页面、动作提交及冲突处理，不能仅新增类型字段。
- `WorkItemSLAState` 尚无当前周期与历史周期的明确投影；应复用后端周期事实，不能因响应考核延期而跳过 SLA 重开与历史展示。
- Shell 的公共操作栏默认关闭，动作由调用方和专业 Panel 承接。这本身不构成缺陷；需逐入口核查公共转派是否复用一致交互，并执行已确认的必填原因、权限、版本和审计契约。
- 并发冲突时保留输入、刷新后由用户确认，属于既有 C2 要求，不再作为新增业务规则重复征求批准。实际前端冲突路径和跨域 E2E 尚未在本次静态核查中验证。

## 5. 开发拆解方式与已确认批次

2026-09-11：维护者同意“后端契约 → 页面操作 → 跨域验收与退役门禁”的顺序，并要求先做设计。细化内容见后续收敛设计；本次不进入业务代码实现。下面的盘点、逐域契约和公共能力工作归入前三批的对应阶段，具体执行拆分待设计审阅后形成计划。

按业务边界交付，不按“HTTP 团队先改、BPMN 团队以后再补”的入口方式留下长期差异：

1. **统一盘点**：对 Incident/Problem/Change 列出每项操作的 HTTP、BPMN、自动化、公共编辑入口，记录专业所有者、写入事实、预期版本、回执、旧路径和验收用例。保留已验证成果，补查遗漏。
2. **逐域完成动作契约**：Incident 按已确认子决策推进设计；Change、Problem 根据角色、生命周期和证据要求分别确认差异。各域完成时同步所有调用方和旧入口退出，不新增通用状态机。
3. **闭合公共能力**：将 R1–R6 纳入身份、通知、权限与重试的既有能力，而不是另开无限扩展的平台工程。API 文档和三个已知后端失败按受影响领域归因。
4. **完整跨域验收**：Incident 恢复→关联 Problem→永久修复 Change→结果验证→Problem 解决；含失败、权限拒绝、版本冲突和重试。Requested Item/generic 的公共路径同时回归。
5. **切换/观察/退役**：完成隔离演练、证据与实际环境准入，不提前物理删除或用未部署代码宣称运行验收完成。

最终计划应写明依赖、每批修改范围、完成标准及未完成事项，不以解决全部评审编号代替完成 WorkItem 重构。

### 公共转派记录：原因必填

2026-09-11：整理者建议自动记录操作人、时间和前后负责人，交接说明选填；维护者明确要求每次转派必须填写原因。本决定取代“说明选填”的建议，并关闭此前 Change、Problem 转派原因是否必填的待讨论项。保留前文讨论历史，不将旧的未确认标记作为当前开发依据。

验收输入：有权操作者提交有效转派及原因后，责任更新和审计记录一起成功；原因缺失或仅为空白时拒绝转派且不产生责任变更。流程与自动化入口同样提供原因、遵守权限和版本约束；重复执行不得重复生成责任变更记录。

### BL-CHG-WO-01：Change 多实施工单（后续迭代）

业务动因：一条 Change 未来可能拆成多个 WorkOrder，由不同人员执行。本轮仅记录需求，不新增模型、接口或页面。后续需要单独确定 WorkOrder 的领域定位及其与 WorkItem、Change、现有 BPMN 任务的关系，并讨论依赖、执行人、移交、结果汇总及关闭条件；不能直接将 WorkOrder 等同于 Catalog Task，也不预先决定新增表或审批机制。

本轮仍须保证现有 Change 主记录和已有流程任务正确运行；多工单能力延期不豁免既有权限、审批、实施前提和审计问题。第 3 节关于实施任务转派的待讨论项仅在修复现有路径确有需要时进一步澄清，不扩展为新的派工功能。

Incident、Change、Problem 的主要责任调整差异及转派原因必填已确认。公共转派记录沿用现有时间线与审计能力，与责任更新同事务保存，不另建交接审批。后续继续收敛公共操作体验和交付范围；尚未确认的新角色、状态或交接机制不能被视为已批准需求。
