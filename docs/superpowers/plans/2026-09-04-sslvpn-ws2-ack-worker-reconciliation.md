# SSLVPN WS2 ACK, Worker Readiness, and Reconciliation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Safely switch the KAF acceptance contract to strict 202 semantics, prove the ITSM Worker scheduler is actually running, and replace audit-log-derived requeue authority with fenced tenant-owned reconciliation state.

**Architecture:** WS2a publishes one OpenAPI/fixture contract and deploys the KAF producer response while the old ITSM consumer remains permissive. Only after production-equivalent evidence does WS2b deploy the strict ITSM consumer. Readiness becomes a shared infrastructure service, while reconciliation is owned by the existing delegated-execution vertical slice and fenced with monotonic Outbox delivery versions.

**Tech Stack:** Go 1.24, Gin, Ent, PostgreSQL, Python 3.12, FastAPI/Pydantic, pytest, OpenAPI 3.1, Docker Compose

**Spec:** `docs/superpowers/specs/2026-09-04-sslvpn-delegation-reliability-hardening-design.md`

## Global Constraints

- Required release order is WS1, WS2a KAF acceptance, WS2b ITSM strict validation, WS3, WS4.
- Do not enable strict ITSM validation before KAF’s new 202 response passes production-equivalent evidence.
- OpenAPI is authoritative; both repositories consume its published fixture artifact and do not hand-maintain competing expected JSON.
- Success is exactly HTTP 202 plus `application/json` and four exact camelCase fields; body limit is 4 KiB.
- Ambiguous responses become `delivery_unknown` and are never automatically or manually requeued.
- API remains unable to construct a KAF dispatcher; Worker remains the only consumer.
- KAF reachability is not a Worker readiness dependency.
- Reconciliation is tenant-owned structured state; AuditLog is evidence only.
