## 4. 部门是树：库内多出的 3,000 个部门基本已解释

**导出文件本身是一棵树**：5,272 个节点、id 全唯一、1 个根（`167ed087…`，名称"组织架构"）、
1 个孤儿（根节点的 `parentId` 是字面量 `"root"`）；深度分布 0→1、1→1、2→128、3→46、4→11、5→13、
6→46、7→217、8→568、9→1225、10→1758、11→881；**深度与 code 长度一一对应**（如深度 10 → 长度 15）。

**库内 7,975 个部门的构成**（相对导出 id 的 3,000 个差额）：

| 归类 | 数量 | 依据 |
| --- | --- | --- |
| 是库内其它 code 的**中间层级**（前缀） | 1,083 | 库内 3,526 个 code 是其它 code 的前缀 |
| 名称出现在用户 `departmentName` **路径分段**中 | **2,323 / 3,000（77.4%）** | 用户文件的 `departmentName` 是形如"组织架构 - … - 财务及会计部"的路径；样例：管理层(380)、后勤支持部门(1927)、财务及会计部(594)、安全及质量风险管理部(55) |
| 仍未对上 | 677 | 如"信息技术部"、"后端开发"、"税务分组"、"上海支持中心" —— 属更细层级 |

**结论**：旧组织树比这份 5,272 节点的部门导出更大；用户的 `departmentName` 路径携带了导出里
**没有**的那部分节点，迁移时把它们也建成部门（这也是为什么库内存在 1,917 个"带真实名称的叶子"
却不在任何部门导出里）。**09-01 副本与 08-04 的 id 集合完全相同**，因此不是副本差异。

### 4.1 3,000 个差额的完整归因（2026-09-15 闭环）

对用户数据做并集取证（`departmentName` 路径按多种分隔符切分，加上 `departmentUnit`、
`userFenzu`、`leader`、`userPost`）后，差额全部落地：

| 归类 | 数量 | 依据 |
| --- | --- | --- |
| 名称在用户数据中有证据 | **2,361（78.7%）** | 路径分段/其它字段命中 |
| 中间层级（是库内其它 code 的前缀） | 158 | 树结构 |
| 叶子且父节点正确（同树的更深节点） | **478** | 如 `…G02 海口项目` → `…G0201 海口`、`…G010902 安全及质量风险管理部` → `…G01090202 网络安全分部` |
| **无法归因的孤立节点** | **3** | `FIN`/财务部、`QA`/测试部、`RD`/研发部：同一批次创建、无父节点、**0 用户挂靠**、通用测试命名 → 判为种子/测试部门，非旧组织 |
