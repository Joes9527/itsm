# Coding Agent 工程协作规范

本规范约束在 ITSM 仓库中执行分析、编码、测试、文档和交付的所有 Coding Agent。目标是保持工程目录可发现、变更可审查、验证可复现，同时不在正常并行开发期间强制迁移既有文件。

## 1. 权威来源与优先级

1. 仓库根目录的 `AGENTS.md` 是产品方向、架构、领域模型、安全和租户边界的权威来源。
2. [`DEVELOPMENT_GUIDE.md`](./DEVELOPMENT_GUIDE.md) 是开发命令、测试、交付和运维流程的权威来源。
3. 本文档规定 Coding Agent 的目录、分支、文档和交付纪律。
4. `docs/` 保存长期有效的项目文档；一次性设计、任务过程稿和本地验证产物不得替代权威文档。

修改架构或领域约束时，必须同步 `AGENTS.md` 和 `CLAUDE.md` 的对应摘要；修改开发流程时，更新 `docs/DEVELOPMENT_GUIDE.md` 或本文档，其他文档只链接，不复制维护同一规则。

## 2. 目录与文件落点

| 内容 | 规范落点 | 说明 |
| --- | --- | --- |
| 后端生产代码 | `itsm-backend/` 内既有领域目录 | 服从已有 vertical slice 或 legacy `controller/` + `service/` 边界。 |
| 前端生产代码 | `itsm-frontend/src/` | 服从 Next.js App Router、领域组件和 `src/lib/api/` 边界。 |
| 后端单元测试 | 被测 Go package 的同目录，命名 `*_test.go` | Go 同包测试可以访问包内实现，是允许且推荐的形式。 |
| 前端单元/组件测试 | 被测模块相邻的 `__tests__/`，命名 `*.test.ts(x)` | 与现有前端测试守卫保持一致。 |
| 后端集成、契约、E2E 与 fixtures | `itsm-backend/tests/{integration,contract,e2e,fixtures,rbac}/` | 跨 package 或真实基础设施验证不得伪装成单元测试。 |
| 前端浏览器 E2E | `itsm-frontend/tests/e2e/` | 按 `flows/`、`roles/` 或 `business-flows/` 分类。 |
| 一次性本地验证 | 本地 worktree、系统临时目录或已忽略产物目录 | 不提交截图、浏览器脚本、日志、导出物或临时验证程序。 |
| 长期项目文档 | `docs/` 下与内容匹配的分类目录 | 同步更新 `docs/README.md` 的入口（如适用）。 |
| 设计决策与实施计划 | `docs/architecture/` 或 `docs/superpowers/{specs,plans}/` | 必须标注 `draft`、`accepted`、`implemented`、`superseded` 或 `archived` 状态。 |
| 历史报告与一次性验收 | `docs/review/` 或 `docs/archive/` | 是否保留由维护者决定，不能留在仓库根目录作为当前入口。 |

### 现有内容的处理边界

本规范自合并后对新增文件和被修改文件生效。既有 `tests/`、`prd/`、`specs/`、`plans/`、`docs/superpowers/`、`memory/` 和根目录历史文件**暂不迁移、删除或改名**。任何整理工作必须单独立项、确认没有并行 Agent 依赖后执行。

## 3. 测试纪律

- 修改业务逻辑、权限、租户、工作流、连接器、AI 工具调用或 API 契约时，必须同步新增或更新对应测试。
- 测试辅助文件必须使用 `_test.go`、`test-utils.ts(x)` 或专用 fixture 目录；不得以普通生产源文件后缀承载仅测试使用的依赖。
- 后端单元测试和前端 `__tests__/` 不要求迁移到根 `tests/`；根 `tests/` 仅允许经明确维护的跨系统验收套件。
- 不得以无理由的测试豁免代替测试。无法自动化的真实路径验证必须写明覆盖范围、环境和未覆盖边界。
- 修改前先运行受影响的最小测试；交付前按影响范围运行构建、类型检查、静态检查、契约检查或端到端验证。

## 4. 文档与报告纪律

- 长期文档使用英文小写 kebab-case 文件名；阶段性报告使用 `yyyy-mm-dd-topic-report.md`。
- 一项规则或事实只维护一个权威来源；其他文档应链接该来源，不得复制出第二份可漂移的规范。
- Agent 的普通完成说明写入 PR 描述，不默认生成并提交报告文件。只有可被后续团队复用的决策、运行手册、验收结论或测试资产才进入 `docs/`。
- 根目录仅允许仓库入口与治理文件：README、许可证、贡献指南、安全政策、变更日志、路线图、Agent 指令及构建/部署配置。不得新增任务回执、截图、临时脚本、浏览器报告或分析报告。
- 历史材料的归档规则遵循 [`documentation-style-guide.md`](./documentation-style-guide.md)。

## 5. 分支与 Worktree 纪律

- 禁止直接向 `main` 提交。
- 每个 Agent 任务使用独立 worktree、独立分支和独立 PR；开始前检查工作区状态，并以最新 `origin/main` 为基线。
- 分支格式统一为：`codex/<type>/<scope>-<short-description>`。
- `<type>` 仅允许：`feat`、`fix`、`refactor`、`docs`、`test`、`chore`、`security`。
- 示例：`codex/fix/rbac-cross-tenant-access`、`codex/docs/agent-engineering-governance`。
- 一个分支只解决一个可审查目标；不得混入无关格式化、清理或其他 Agent 的修改。
- 最终提交遵循 Conventional Commits；PR 必须说明目标、影响范围、验证证据、风险和未验证项。

## 6. Agent 交付门禁

提交或请求评审前，Agent 必须：

1. 检查新增或变更文件的目录落点符合本文档。
2. 说明是否影响架构、领域、权限、租户、工作流、连接器、AI 调用或 API 契约。
3. 运行与变更相称的验证，并如实说明未运行项与原因。
4. 执行 `git diff --check`，确认无敏感信息、临时文件、构建产物和无关变更。
5. 对未知、未注册或无权限的分发目标显式失败；不得静默跳过或报告成功。

## 7. 任务协同与角色分工

### 任务准入（Definition of Ready）

开始实现前，任务说明或 PR 草案必须写明：

1. 单一目标，以及明确不在本任务处理的范围。
2. 影响的模块、API、数据模型、权限、租户、工作流、连接器或外部依赖。
3. 是否会写入共享数据库、执行迁移、初始化数据、RLS 切换或批量修复。
4. 计划使用的测试、真实路径验收方式和完成条件。
5. 已知依赖、冲突分支和正在进行的相关任务。

信息不足时，Agent 应先调查或请求澄清；不得以假设扩展任务范围。

### 职责分离

协同开发可由不同 Agent 分担以下职责：

| 角色 | 职责 | 不可替代的控制点 |
| --- | --- | --- |
| 设计/拆解 | 定义边界、契约、验收条件和依赖顺序 | 不把历史设计稿当作当前契约。 |
| 实现 | 在已批准范围内完成可审查的改动 | 不混入无关重构或治理迁移。 |
| 审查 | 独立检查领域规则、权限、租户、并发与回归风险 | 不只复述实现者的结论。 |
| 集成 | 决定合并顺序、处理冲突并确认最终验证 | 不合并存在未解释风险或未满足依赖的变更。 |

涉及 WorkItem、RBAC、tenant/MSP、BPMN、数据库迁移、连接器、AI 工具调用或安全边界的变更，必须由独立审查者或维护者复核；实现 Agent 不能作为唯一验收者。

## 8. 共享环境与数据库变更

- 共享 Postgres、Redis、Docker 服务和 CI runner 不是任一 Agent 的私有沙箱；具体拓扑与风险见 [`DEVELOPMENT_GUIDE.md`](./DEVELOPMENT_GUIDE.md)。
- 包含 schema 迁移、数据回填、初始化/清理、RLS 模式变更或批量写入的任务，必须在任务准入时标记为“共享环境变更”。
- 同一时间只允许一个经协调的共享数据库写入任务执行实际变更；其他 Agent 使用隔离测试库、mock、只读查询或等待该任务完成。
- 执行前必须记录目标环境、前置检查、影响范围、回滚或补救方式；执行后必须记录实际结果和验证证据。
- 不得把开发环境的数据清理、数据库重置或迁移执行当成普通单元测试的副作用。

## 9. 质量门禁与合并顺序

### 任务门禁

实现 Agent 在请求评审前完成受影响范围的最小测试、构建/类型检查/静态检查，以及本规范第 6 节的交付检查。

### 合并门禁

集成前必须确认：

1. 必需 CI、API 契约和受影响的真实路径验证已有证据。
2. 依赖分支、迁移和配置变更已经按正确顺序合并或发布。
3. 没有未解释的共享环境风险、测试豁免或并行修改冲突。
4. PR 仅包含声明范围内的变更，并有清晰的回滚边界。

若多个 PR 修改同一 API、数据表、工作流定义或权限策略，集成负责人必须先确定合并顺序；不得以“先合并再修”替代集成设计。

## 10. 决策索引与治理度量

- 重大架构、数据模型、权限和跨模块契约决策必须有一个权威文档，并标明状态、负责人、影响范围、替代方案和取代关系。
- `docs/README.md`、`AGENTS.md` 或相应领域文档应能找到当前有效决策；被取代的设计稿必须标为 `superseded` 或 `archived`。
- 每个迭代至少复盘一次：PR 首次通过率、返工次数、CI 失败与 flaky test、并行冲突、临时产物误入库次数，以及从任务开始到真实路径验收的周期。
- 度量用于发现流程瓶颈，不以提交数量、行数或 Agent 活跃时长评价交付质量。

## 11. 采用与后续治理方式

本规范不触发自动迁移。后续若要整理测试目录、根目录报告或历史文档，维护者应创建独立治理任务，先盘点调用方、CI 引用和并行 Agent 依赖，再以可回滚的小批次执行。

自动化门禁按以下节奏推进：

1. 先以文档和 PR 自检清单执行一个迭代。
2. 对目录、分支、临时产物和测试落点增加 CI 告警，观察误报与实际阻塞。
3. 仅对已稳定、低误报的规则升级为 CI 阻断；迁移类规则仍按独立治理任务执行。
