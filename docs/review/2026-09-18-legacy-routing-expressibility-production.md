## 2. 关键发现：1085 条里有 128 条不是工单派单

按 `definitionId` 拆分后，`taskDefKey` 暴露了真实用途：

| 归口 | 流程定义 | 行数 | 去重任 | 失效引用 |
| --- | --- | --- | --- | --- |
| **工单派单** | `orderRequest`(634) + `sj002`(321) + `SJ001`(2) | **957** | 112 | **85 行 / 22 个 id** |
| **知识库审批流** | `knowledgeProcess` | **128** | 15 | 12 行 / 2 个 id |

`knowledgeProcess` 的节点是 `KNOWLEDGE_ADMIN` / `KNOWLEDGE_MANAGER` / `establish`——这是**知识条目的审批与定稿**，不是工单派单。而且**全部 81 条"固定角色"型都在这条流里**（establish 40 角色 + KNOWLEDGE_MANAGER 40 角色 + KNOWLEDGE_ADMIN 1 角色）。

**因此"1085 条派单路由"这个口径**把工单派单（957）与知识库审批（128）混在了一起。两者应分别定迁移范围。

### ⚠️ 与计划 §4 表格不一致，原因已查明

计划的《流程与路由》设计 §4 给的是 **6 / 12 / 821 / 246**（合计 1085）。本重算得到 **872 / 85 / 0 / 0**（工单派单口径 957）。**两者不是同一个判据**：

- **本次重算只校验了两件事**：① 找人方式在目标模式集内；② 目标人在旧身份表中存在。
- **计划 §4 的表显然用了更严格的判据**（很可能还要求：旧分类 `ctiId` 能在**新 CTI 树**中对上、以及流程定义在新系统有对应物）。

因此 **872 是"直接可表达"的上界**，不是最终可迁数。本文件**不宣称**计划 §4 的表是错的，只指出：两者判据不同，**不可混用**。

### 首期可迁移范围的建议判据（需在 Task 4/5 之前补齐）

要把上界收紧为可执行清单，还需补三项只读校验（本 Task 未做，属《分类对齐》与《人员裁定》的范围）：

3. 3 个派单流程定义（orderRequest / sj002 / SJ001）在新系统是否有承载流程。
